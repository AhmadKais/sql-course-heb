## 1. מה זה אילוץ, ולמה בלעדיו אין מערכת

<div align="center">

**חוק עסקי הוא משפט בעברית. אילוץ הוא אותו משפט — כתוב במקום שבו אי אפשר להפר אותו.**

</div>

במודול 4 למדנו לתעד חוקים עסקיים. עכשיו נלמד **לאכוף** אותם.

ההבדל הוא הכול:

| | חוק עסקי | אילוץ |
|---|-----------|--------|
| מה זה | משפט במסמך | כלל בבסיס הנתונים |
| מי מכיר אותו | מי שקרא את המסמך | **המערכת עצמה** |
| מה קורה כשמפרים | אף אחד לא שם לב | הפעולה **נדחית** |
| מתי הוא פועל | כשמישהו זוכר | **תמיד** |

> 🎬 **סיפור מהשטח: התאריך שנסע אחורה**
>
> מערכת השכרת רכב אפשרה להזין תאריך החזרה. בטופס באתר הייתה בדיקה יפה: אי אפשר לבחור תאריך החזרה מוקדם מתאריך האיסוף. הכול תקין.
>
> אחרי שנתיים הוסיפו **אפליקציה לנייד**. צוות אחר, קוד אחר. את הבדיקה הזאת שכחו.
>
> תוך חודש נוצרו במערכת 340 השכרות שהוחזרו **לפני** שנאספו. חלקן בטעות משתמשים, חלקן באג באזור זמן. מערכת החיוב חישבה משך שלילי, וכמה לקוחות **קיבלו זיכוי** על נסיעות שביצעו.
>
> **הבעיה:** החוק "תאריך החזרה ≥ תאריך איסוף" נאכף ב**טופס**, לא ב**נתונים**. טופס הוא דלת אחת מיני רבות; בסיס הנתונים הוא הקיר.
>
> 🔑 **הכלל:** אילוץ שיושב באפליקציה מגן על מי שנכנס דרך האפליקציה. אילוץ שיושב בבסיס הנתונים מגן על **כולם** — כולל ייבוא קבצים, סקריפט תחזוקה, ומפתח שמריץ `UPDATE` ידני בשלוש לפנות בוקר.

## 3. תחום (Domain) — האילוץ שכולם שוכחים

<div align="center">

**תחום הוא הגדרת קבוצת הערכים החוקיים שמאפיין יכול לקבל.**

</div>

זה נשמע טכני ומשעמם. בפועל, **רוב הנתונים המלוכלכים בעולם נובעים מהיעדר תחומים**.

### מה תחום כולל

| הרכיב | דוגמה | מה קורה בלעדיו |
|-------|--------|-----------------|
| **סוג נתון** | תאריך, מספר, טקסט | תאריך שנשמר כטקסט: `"3 במרץ"`, `"03/03"`, `"מחר"` |
| **אורך / דיוק** | מחיר: 8 ספרות + 2 עשרוניות | מחיר `19.999` שמוצג כ‑`20.00` ומחושב כ‑`19.999` |
| **טווח** | גיל: 0–120 · אחוז: 0–100 | עובד בן 900. הנחה של 4000% |
| **רשימת ערכים** | סטטוס: `פעיל` / `מוקפא` / `סגור` | `"פעיל"`, `"פעילה"`, `"Active"`, `"פעיל "` — ארבעה סטטוסים במקום אחד |
| **פורמט** | ת"ז: 9 ספרות + ספרת ביקורת | `"12345"`, `"123-45-678"`, `"אין"` |
| **חובה / רשות** | לחיה **חייב** להיות מין; שם — רשות | חיה בלי מין = שורה חסרת ערך |
| **ברירת מחדל** | `תאריך_יצירה = היום` | שדה ריק שאיש לא יודע למה |

### 🎬 סיפור מהשטח: שדה הסטטוס שהיה בו 47 ערכים

חברת שירות שמרה את סטטוס הפנייה כטקסט חופשי. הרעיון היה גמישות.

אחרי ארבע שנים ביקשה ההנהלה דוח: *"כמה פניות פתוחות?"*

בשאילתה התגלו **47 ערכים שונים** בשדה: `פתוח`, `פתוחה`, `Open`, `בטיפול`, `בטיפול!`, `ממתין ללקוח`, `ממתין`, `פתוח - דחוף`, `פתוח (חוזר)`, `פתוח ‏` (עם רווח בסוף), ועוד 38 וריאציות.

אף אחד לא ידע אילו מהם נחשבים "פתוח". הדוח נדחה בשבועיים, מיפוי ידני עלה 60 שעות עבודה, ובסוף — בנו טבלת `סטטוסים` עם 6 ערכים.

> 🔑 **הלקח:** "גמישות" בשדה סטטוס אינה תכונה. היא **דחיית ההחלטה** — והחוב נגבה בריבית ביום שמישהו מבקש דוח.

### שתי דרכים לממש תחום מסוג רשימה

</div>

```text
Method A -- value list defined on the column      Method B -- code table
+--------------------------------+         +--------------------------+
| ANIMAL                         |         | STATUS                   |
|   status  in {AVAILABLE,       |         |  # status_code           |
|               ADOPTED,         |         |  * description           |
|               MEDICAL,         |         |  * is_active             |
|               QUARANTINE}      |         |  o display_order         |
+--------------------------------+         +------------+-------------+
                                                        | 1
      [+] simple, fast                                  |
      [-] adding a value = schema change                | M
      [-] no room for description, order, colour +------+-----------+
                                                |  ANIMAL          |
      Good for: a small list that never changes |   * status_code  |
      (male/female, yes/no)                     +------------------+

                                          [+] adding a value = a new row
                                          [+] description, order, deactivate
                                          [-] one more table, one more join

                                          Good for: everything else
```

<div dir="rtl">

> 💡 **כלל אצבע:** אם יש סיכוי שהלקוח יבקש להוסיף ערך אחרי שהמערכת עלתה לאוויר — **טבלה**. אם הרשימה קבועה מאז ומעולם ולא תשתנה (זכר/נקבה, ימי השבוע) — רשימה מוגדרת.

## 4. אילוצי התייחסות וכללי מחיקה

מפתח זר חייב להצביע על שורה שקיימת. זה מובן מאליו. **מה שלא מובן מאליו הוא מה קורה כשמוחקים את השורה שאליה מצביעים.**

</div>

```text
                    Delete a department that has 12 employees.
                    What happens to the employees?

  +------------------+------------------+---------------------------+
  |  RESTRICT        |  CASCADE         |  SET NULL                 |
  |  (NO ACTION)     |                  |                           |
  +------------------+------------------+---------------------------+
  | Delete refused.  | The 12 employees | The 12 employees stay,    |
  | "There are       | are deleted too. | but their department      |
  |  employees here" |                  | field becomes empty.      |
  +------------------+------------------+---------------------------+
  | [+] safest       | (!) very dangerous| (!) ONLY if the relation |
  | the correct      | but sometimes    |     is optional!          |
  | default          | necessary        |                           |
  +------------------+------------------+---------------------------+
  | dept -> employees| order -> lines   | employee -> manager       |
  | invoice -> cust. | post -> comments | (manager left, employee stays) |
  +------------------+------------------+---------------------------+
```

<div dir="rtl">

**איך מחליטים?** שאלה אחת:

<div align="center">

**"האם הילד יכול להתקיים בלי ההורה?"**

</div>

| התשובה | הכלל | הדוגמה |
|---------|------|---------|
| לא, הוא **חלק** ממנו | `CASCADE` | שורת הזמנה בלי הזמנה = חסרת משמעות |
| כן, הוא עצמאי | `RESTRICT` | עובד קיים גם אם המחלקה נסגרת — קודם העבירו אותו |
| כן, וההפניה אופציונלית | `SET NULL` | עובד בלי מנהל זה מצב חוקי |

> ⚠️ **אזהרה על `CASCADE`:** הוא מוחק בשקט, בשרשרת, ובלי לשאול. מחיקת לקוח יכולה לגרור הזמנות ⟵ שורות הזמנה ⟵ החזרות ⟵ חשבוניות. **תמיד עקבו אחר השרשרת עד הסוף לפני שמפעילים אותו.**
>
> 💡 וזכרו את מודול 5: **ברוב המערכות העסקיות לא מוחקים בכלל.** מסמנים `is_active = false`. אז שאלת כלל המחיקה בכלל לא עולה.

## 5. קשת (Arc) — "או‑או" בלעדי

במודול 3 ראינו קשת בתרשים. עכשיו נבין אותה לעומק.

<div align="center">

**קשת מסמנת: מבין היחסים שהיא מקיפה, בדיוק אחד יתקיים בכל מופע.**

</div>

### 5.1 הבעיה שהקשת פותרת

</div>

```text
The business:  "Every payment comes from a private person OR a company.
                Never from both, always from one."

[X] WITHOUT an arc -- two optional relationships:

   +------------+                          +------------+
   |  PERSON    |                          |  COMPANY   |
   +------+-----+                          +-----+------+
          | o                                    | o
          +--------------+          +------------+
                         |          |
                    +----+----------+----+
                    |      PAYMENT       |
                    |  o person_id  (FK) |
                    |  o company_id (FK) |
                    +--------------------+

   What this model actually ALLOWS:
     [OK] payment with person_id only         <- wanted
     [OK] payment with company_id only        <- wanted
     [X]  payment with BOTH                   <- forbidden! whose money is it?
     [X]  payment with NEITHER                <- forbidden! orphan money


[OK] WITH an arc:

   +------------+                          +------------+
   |  PERSON    |                          |  COMPANY   |
   +------+-----+                          +-----+------+
          |                                      |
          +----------.              .------------+
                     '--------------'   <- the ARC
                            |
                    +-------+--------+
                    |    PAYMENT     |
                    +----------------+

   Now the model says explicitly:  one. Exactly one. Always.
```

<div dir="rtl">

### 5.2 שלושת כללי הקשת

| # | הכלל | למה |
|---|------|------|
| 1 | כל היחסים בקשת יוצאים **מאותה ישות** | הקשת מתארת בחירה של מופע אחד |
| 2 | לכולם **אותה אופציונליות** — כולם חובה או כולם רשות | אחרת "בדיוק אחד" חסר משמעות |
| 3 | לכולם **אותה עוצמה (Cardinality)** בצד הישות | אחרת אלה לא באמת חלופות |

> ⚠️ **הפרה נפוצה:** קשת שבה יחס אחד חובה והשני רשות. זה לא קשת — זה בלבול. אם `PERSON` חובה ו‑`COMPANY` רשות, אז בעצם **תמיד** יש אדם, והחברה היא סתם תוספת. תקנו את המודל או ותרו על הקשת.

### 5.3 קשת מול טיפוס משנה — ההחלטה הקשה

זו השאלה הכי נפוצה בפרק, ושתי האפשרויות **נראות** דומות:

</div>

```text
Same business, two models:

Model A -- ARC                        Model B -- SUBTYPE
+----------+   +----------+          +---------------------------+
| PERSON   |   | COMPANY  |          |        PAYER              |
+----+-----+   +----+-----+          |  # payer_id               |
     '------.  .----'                |  * name                   |
            '-'                      | +-----------+-----------+ |
            |                        | |  PERSON   |  COMPANY  | |
      +-----+------+                 | | * id_num  | * reg_num | |
      |  PAYMENT   |                 | +-----------+-----------+ |
      +------------+                 +-------------+-------------+
                                                   | 1
                                                   | M
                                            +------+------+
                                            |   PAYMENT   |
                                            +-------------+
```

<div dir="rtl">

**ההכרעה — שלוש שאלות:**

| השאלה | ⟵ קשת | ⟵ טיפוס משנה |
|--------|--------|----------------|
| האם לשתי הישויות יש **הרבה מאפיינים משותפים**? | לא, הן שונות מאוד | כן, רובם משותפים |
| האם **ישויות אחרות** צריכות גם הן להצביע על "אחד מהשניים"? | לא, רק זו | כן, שלוש‑ארבע ישויות |
| האם הן קיימות ב**עולם** בזכות עצמן? | כן, לגמרי | פחות — הן וריאציות של רעיון אחד |

<div align="center">

**כלל אצבע: קשת אחת ⟵ בסדר. אותה קשת חוזרת בשלושה מקומות ⟵ בנו טיפוס על.**

</div>

> 🎬 **סיפור מהשטח: הקשת שהתרבתה**
>
> מערכת נדל"ן ייצגה "בעלים" בקשת: `נכס` שייך ל`אדם` או ל`חברה` או ל`עמותה`.
>
> אחר כך הוסיפו `חוזה` — גם לו יש בעלים. עוד קשת בת שלושה ענפים.
> אחר כך `תשלום` — עוד קשת. `מסמך` — עוד אחת. `התכתבות` — עוד אחת.
>
> **חמש קשתות זהות בחמישה מקומות.** כשהוסיפו סוג בעלים רביעי (נאמנות), נדרש שינוי בחמישה מקומות. פספסו אחד. מסמכים של נאמנויות פשוט לא נשמרו במשך חודשיים.
>
> **הפתרון שהיה נכון מלכתחילה:** טיפוס על `בעלים` עם ארבעה טיפוסי משנה. סוג חדש = טבלה אחת חדשה, ואף אחד מהחמישה לא מושפע.

### 5.4 איך קשת נראית בטבלאות

זו הנקודה שמפתיעה תלמידים: **בבסיס נתונים רלציוני אין "קשת".** צריך לממש אותה.

</div>

```text
Method A -- two foreign keys + a CHECK constraint   * the common one
+------------------------------------------------------+
| PAYMENT                                              |
|   payment_id                                         |
|   amount                                             |
|   person_id    o  FK -> PERSON                       |
|   company_id   o  FK -> COMPANY                      |
|                                                      |
|   CHECK ( (person_id IS NOT NULL AND company_id IS NULL)  OR
|           (person_id IS NULL AND company_id IS NOT NULL) )|
+------------------------------------------------------+
   [+] simple, the foreign keys are real
   [-] one column is always empty
   [-] with 5 branches the condition becomes a monster

Method B -- a type column + an id column
+------------------------------------------------------+
| PAYMENT                                              |
|   payer_type   *  in {PERSON, COMPANY}               |
|   payer_id     *                                     |
+------------------------------------------------------+
   [+] stays narrow even with 10 branches
   [-] (!) NO real foreign key! The database cannot validate it
   [-] the system loses referential integrity -- exactly what we wanted to keep

Method C -- a supertype (as shown above)
   [+] one real, clean foreign key
   [-] one more table
```

<div dir="rtl">

> 🔑 **ההמלצה:** שיטה א' עד שלושה ענפים. מעבר לזה — עברו לטיפוס על (שיטה ג'). **הימנעו משיטה ב'** אלא אם אין ברירה: היא מוותרת על שלמות התייחסותית, וזה ויתור כבד.

## 6. יחסים היררכיים ורקורסיביים

במודול 5 ראינו יחס רקורסיבי. עכשיו נעצב **היררכיה שלמה**.

### 6.1 ההיררכיה הקלאסית

</div>

```text
Org chart:                              Implementation -- recursive 1:M

        CEO                             +-------------------------+
         |                              | EMPLOYEE                |
    +----+----+                         +-------------------------+
   VP        VP                         | # employee_id           |
 Marketing  Dev                         | * name                  |
    |         |                         | o manager_id  (FK)  ----+--.
  +-+-+     +-+--+                      +-------------------------+  |
 Dana Yossi Maya Amit                                ^               |
                                                     '---------------'
                                                  "points to another employee
                                                   in the SAME table"

The data:
+-----+----------+------------+
| id  | name     | manager_id |
+-----+----------+------------+
| 1   | CEO      | NULL       |  <- the ROOT! so the reference MUST
| 2   | VP Mkt   | 1          |     be optional
| 3   | VP Dev   | 1          |
| 4   | Dana     | 2          |
| 5   | Yossi    | 2          |
+-----+----------+------------+
```

<div dir="rtl">

**שלושה כללים שחייבים להתקיים בהיררכיה:**

| # | הכלל | מה קורה בלעדיו |
|---|------|-----------------|
| 1 | ההפניה להורה **חייבת להיות אופציונלית** | לשורש אין הורה — בלי NULL אי אפשר להכניס אף שורה |
| 2 | **אסור** שרשומה תהיה ההורה של עצמה | `manager_id = employee_id` — לולאה |
| 3 | **אסור** מעגל בשרשרת | א' מנהל את ב', ב' מנהל את ג', ג' מנהל את א' — המערכת תרוץ לנצח |

> ⚠️ כלל 2 קל לאכוף (`CHECK manager_id <> employee_id`). **כלל 3 קשה מאוד** — אין דרך פשוטה לאכוף אותו במבנה הטבלה, וצריך בדיקה בקוד או טריגר. זהו אחד המקומות שבהם אילוץ אינו מספיק והמערכת חייבת לעזור.

### 6.2 המחיר של היררכיה: "כמה עמוק?"

</div>

```text
The question:  "Who reports to the CEO, at ALL levels?"

With a recursive hierarchy:
   level 1:  SELECT ... WHERE manager_id = 1
   level 2:  SELECT ... WHERE manager_id IN (result of level 1)
   level 3:  SELECT ... WHERE manager_id IN (result of level 2)
   ...       and when do you stop? Nobody knows in advance!

-> This is a "recursive query". It's possible (WITH RECURSIVE / CONNECT BY),
   but it is neither simple nor fast.
```

<div dir="rtl">

**שלוש דרכים להתמודד:**

| הגישה | איך | מתי מתאים |
|--------|------|------------|
| **שאילתה רקורסיבית** | `CONNECT BY` (Oracle) / `WITH RECURSIVE` | עומק לא ידוע, שינויים תכופים |
| **עומק קבוע** | עמודות `רמה_1`, `רמה_2`, `רמה_3` | ⚠️ **רק** אם ההיררכיה באמת חסומה (למשל: מדינה⟵מחוז⟵עיר) |
| **נתיב שמור** | עמודה `path = "/1/2/4/"` | קריאה מהירה מאוד, כתיבה מסובכת |

> 💡 **המלצה מעשית:** התחילו מיחס רקורסיבי פשוט. אל תסבכו מראש. אם מסתבר שהשאילתות איטיות מדי — **אז** מוסיפים עמודת נתיב כאופטימיזציה מודעת. זו החלטה של מודול 12, לא של עכשיו.

### 6.3 היררכיה מול M:M רקורסיבי — לא לבלבל

</div>

```text
(1) HIERARCHY  recursive 1:M             (2) NETWORK  recursive M:M
   "each one has ONE parent"                "each has several, and each has several"

        A                                     A ---- B
       / \                                    | \  / |
      B   C                                   |  \/  |
     / \                                      |  /\  |
    D   E                                     C ---- D

   employee -> manager                    part -> made of parts
   category -> parent category            friend -> friend
   folder -> parent folder                course -> prerequisite

   Implementation: ONE column (parent_id)  Implementation: a separate link table!

   -> a TREE                              -> a GRAPH
```

<div dir="rtl">

**המבחן המכריע:** *"כמה הורים יכולים להיות לפריט אחד?"*
אחד ⟵ עמודה. יותר מאחד ⟵ טבלה מקשרת.

> 🎬 **סיפור מהשטח: הגור עם אמא אחת**
>
> במודל של מקלט לבעלי חיים שרטטו יחס רקורסיבי: `אמא ⟵ גורים`. עמודה אחת, `mother_id`. מושלם.
>
> אחרי חצי שנה ביקשה מנהלת המקלט לתעד גם את **האב** — בגלל שאלות של גזע וגנטיקה.
>
> עמודה שנייה, `father_id`? עובד, אבל מסריח: מה יקרה כשירצו לתעד "אח מאותה המלטה"? עוד עמודה?
>
> **הפתרון הנכון:** לא שני יחסים רקורסיביים, אלא **ישות `PARENTAGE`** עם `child_id`, `parent_id` ו‑`parent_role` (אם/אב). עכשיו אפשר להוסיף תפקידים בלי לגעת במבנה, ולתמוך בכל הצירופים.
>
> 🔑 **הלקח:** ברגע שאתם מוסיפים "עוד עמודה מאותו סוג" — עצרו. זו הפרת 1NF שמתחפשת ליחס רקורסיבי.

## 7. עיצוב מידע היסטורי

<div align="center">

**רוב המערכות שומרות מה שיש. מערכות טובות שומרות גם מה שהיה.**

</div>

### 7.1 השאלה שמפילה מודלים

</div>

```text
The simple model:              Questions it CANNOT answer:

+------------------+          [X] "Which department was Dana in during 2024?"
| EMPLOYEE         |          [X] "When did she move?"
+------------------+          [X] "Who was her manager back then?"
| # employee_id    |          [X] "How many employees were in Marketing a year ago?"
| * name           |          [X] "What was her salary when she got the bonus?"
| * salary         |
| * department_id  |  <- this column holds ONLY the present.
+------------------+     the moment you update it -- the past is erased forever.
```

<div dir="rtl">

**זו לא בעיה טכנית. זו החלטת עיצוב שחייבים לקבל מראש**, כי מידע שלא נשמר — אבד.

### 7.2 שלוש רמות של שמירת היסטוריה

</div>

```text
LEVEL 0 -- no history
+--------------------------+
| EMPLOYEE                 |   "Dana works in Marketing"
|  department_id = 7       |   <- an update erases the past
+--------------------------+

LEVEL 1 -- timestamps (who changed it, and when)
+--------------------------+
| EMPLOYEE                 |   "Dana works in Marketing,
|  department_id = 7       |    last change: 01/03 by Ronit"
|  last_modified           |   <- we know there WAS a change, not FROM what
|  last_modified_by        |
+--------------------------+

LEVEL 2 -- a full history entity  *
+------------------+         +----------------------------+
| EMPLOYEE         |    1    | EMPLOYEE_ASSIGNMENT        |
+------------------+---------+----------------------------+
| # employee_id    |    M    | # assignment_id            |
| * name           |         | * employee_id      (FK)    |
+------------------+         | * department_id    (FK)    |
                             | * start_date               |
   <- the department is      | o end_date    (NULL=current)|
      no longer HERE!        | o salary                   |
                             +----------------------------+

   Dana:  Marketing   01/01/2023 -> 31/12/2024
          Development 01/01/2025 -> NULL   (current)

   [OK] now all five questions above can be answered
```

<div dir="rtl">

### 7.3 הדפוס: ישות "תקופה"

זהו הדפוס החוזר בכל עיצוב היסטורי:

| הרכיב | התפקיד | הערה |
|--------|---------|-------|
| `start_date` | מתי התקופה התחילה | **חובה** |
| `end_date` | מתי הסתיימה | **אופציונלי** — `NULL` פירושו "עד היום" |
| הערך עצמו | מה היה נכון בתקופה | מחלקה, שכר, מחיר, סטטוס |

**וארבעה אילוצים שחייבים ללוות אותו:**

</div>

```text
(1) end_date >= start_date                  <- a simple CHECK constraint

(2) NO OVERLAP between periods of the same entity
   +--------------+
   | 01/01 -> 30/06|
   +--------------+
          +--------------+
          | 01/05 -> 31/12|   [X] Dana in two departments in May-June?
          +--------------+

(3) AT MOST ONE open period  (end_date IS NULL)
   otherwise: Dana has two "current" departments

(4) NO GAPS (if the business requires continuity)
   +------------+        +------------+
   | 01/01->30/06|        | 01/09->NULL |   <- where was Dana in July-August?
   +------------+        +------------+
                    ^
              a two-month gap -- legal? depends on the business. ASK the client!
```

<div dir="rtl">

> ⚠️ **אילוצים ② ו‑③ אינם ניתנים לאכיפה במפתח ייחודי רגיל.** הם דורשים טריגר או בדיקה בקוד. זהו מקרה קלאסי של חוק עסקי ברמת אכיפה ② (טריגר), כפי שלמדנו במודול 4.

### 7.4 מתי כן ומתי לא לשמור היסטוריה

היסטוריה עולה: עוד טבלאות, שאילתות מסובכות יותר, יותר נתונים.

| שמרו היסטוריה כאשר... | אל תשמרו כאשר... |
|------------------------|-------------------|
| יש חובה חוקית או רגולטורית | הערך לא מעניין אף אחד בדיעבד |
| כסף מעורב (מחירים, שכר, חיובים) | הוא נגזר וניתן לחישוב מחדש |
| מישהו יבקש דוח "לפי תאריך X" | אין שאלה עסקית שמצדיקה זאת |
| צריך לחקור "מי שינה ומתי" | הנתון מתעדכן כל שנייה (טמפרטורה בחיישן) |

> 🎬 **סיפור מהשטח: מי אישר את ההנחה?**
>
> רשת חנויות אפשרה למנהלי סניפים לאשר הנחות עד 15%. הנחות גדולות יותר דרשו אישור סמנכ"ל.
>
> בביקורת שנתית התגלו 60 הנחות של 40% שאושרו במהלך השנה. המערכת שמרה בהזמנה שדה `approved_by` — מפתח זר לעובד.
>
> אבל שניים מאותם "מאשרים" כבר לא עבדו בחברה, **ותפקידם במערכת עודכן ל"לא פעיל"**. שלישי עבר תפקיד והיה עכשיו רשום כ"סמנכ"ל" — אף שבזמן האישור היה עוזר.
>
> **אי אפשר היה לקבוע אם ההנחות אושרו כדין.** הביקורת נסגרה בממצא "לא ניתן לאימות".
>
> 🔑 **הלקח:** במסמך שמתעד **החלטה**, שומרים לא רק *מי* — אלא **באיזה תפקיד הוא היה באותו רגע**. זה ערך מוקפא, בדיוק כמו מחיר.

## 8. דוגמה מלאה — מערכת חניה

נראה את כל האילוצים ביחד. **העסק:** חניון עירוני.

</div>

```text
The client's rules, as stated in the interview:

  1. "Every subscription has a parking permit with a unique number"
  2. "A subscription belongs to a resident OR a business -- one of them, not both"
  3. "The residents' rate changes every year, but a subscriber pays what it was when they signed up"
  4. "The parking lot is divided into zones, and a zone into rows"
  5. "A car cannot enter twice without exiting"
  6. "Subscription status: active, frozen, cancelled"
  7. "A frozen subscription cannot enter"
```

<div dir="rtl">

**התרגום לאילוצים:**

| # | החוק | סוג האילוץ | המימוש |
|---|------|-------------|---------|
| 1 | תו ייחודי | **מזהה משני** | `UNIQUE(permit_number)` |
| 2 | תושב או עסק | **קשת** | שני FK + `CHECK` בלעדי |
| 3 | תעריף קפוא | **ערך היסטורי** | `rate_paid` בתוך `SUBSCRIPTION` |
| 4 | אזור ⟵ שורה | **היררכיה** | יחס רקורסיבי `parent_zone_id` |
| 5 | אין כניסה כפולה | **אילוץ מורכב** | טריגר: אין רשומה פתוחה (`exit_time IS NULL`) |
| 6 | שלושה סטטוסים | **תחום** | טבלת קוד `STATUS` |
| 7 | מוקפא לא נכנס | **אילוץ מורכב** | בדיקה בזמן כניסה — טריגר או קוד |

</div>

```text
The model:

+--------------+         +--------------+
|  RESIDENT    |         |  BUSINESS    |
+-------+------+         +------+-------+
        '----------.   .--------'
                   '---'  <- ARC: resident or business
                     |
          +----------+-----------------+
          | SUBSCRIPTION               |
          +----------------------------+
          | # subscription_id          |
          | * permit_number  <- UNIQUE |      +---------------------+
          | * rate_paid      <- FROZEN!|      | ZONE                |
          | * status_code    (FK)      |      +---------------------+
          | * start_date               |      | # zone_id           |
          | o end_date                 |      | * name              |
          +----------+-----------------+      | o parent_zone_id ---+-.
                     | 1                      +----------+----------+ |
                     |                             ^     | 1          |
                     | M                           '-----+------------'
          +----------+-----------------+                 |  hierarchy
          | PARKING_EVENT              |                 | M
          +----------------------------+                 |
          | # event_id                 |<----------------'
          | * entry_time               |
          | o exit_time  (NULL = inside)|
          | * zone_id       (FK)       |
          +----------------------------+

     The constraint that prevents double entry:
       "no more than ONE row with exit_time IS NULL per subscription"
       <- exactly the same pattern as "one open period" in section 7.3!
```

<div dir="rtl">

> 💡 שימו לב שאילוץ "אין כניסה כפולה" ואילוץ "תקופה פתוחה אחת" הם **אותו אילוץ בדיוק**. ברגע שמזהים את הדפוס, הוא חוזר בכל מקום: השאלה, השכרה, אשפוז, מנוי, משמרת.

## 9. חמש טעויות נפוצות

| # | הטעות | למה זו טעות | התיקון |
|---|-------|--------------|---------|
| 1 | לאכוף חוקים רק באפליקציה | כל דלת אחרת (ייבוא, סקריפט, API) עוקפת אותם | אילוץ בבסיס הנתונים כשכבה אחרונה |
| 2 | קשת שבה יחס אחד חובה והשני רשות | זה לא "או‑או" — זה בלבול | תקנו לאותה אופציונליות, או ותרו על הקשת |
| 3 | `CASCADE` כברירת מחדל | מוחק בשקט שרשרת שלמה | `RESTRICT` כברירת מחדל; `CASCADE` רק לחלקים אמיתיים |
| 4 | יחס רקורסיבי בלי NULL בהורה | לשורש אין הורה — אי אפשר להכניס שום שורה | ההפניה להורה **תמיד** אופציונלית |
| 5 | להוסיף "עוד עמודה מאותו סוג" | `mother_id` + `father_id` + `sibling_id`... | זו הפרת 1NF — צריך ישות מקשרת |

## 11. סיכום המודול

<div align="center">

### 🧠 שבע נקודות שחייבים לצאת איתן

</div>

1. **חוק עסקי שלא הפך לאילוץ הוא בקשה מנומסת.** האפליקציה היא דלת אחת; בסיס הנתונים הוא הקיר.
2. **שלושת סוגי האילוצים המרכזיים:** מזהים ייחודיים (מודול 6), **קשתות**, ו**תחומים**. בנוסף: שלמות התייחסותית ואילוצים מורכבים.
3. **תחום הוא האילוץ המוזנח ביותר** — ומקור רוב הנתונים המלוכלכים. שדה סטטוס כטקסט חופשי הוא באג שממתין לקרות.
4. **קשת = "בדיוק אחד מבין".** שלושה כללים: אותה ישות, אותה אופציונליות, אותה עוצמה. בטבלאות היא מיוצגת ב‑`CHECK`, לא בקסם.
5. **קשת אחת בסדר; קשת שחוזרת בשלושה מקומות אומרת "בנו טיפוס על".**
6. **בהיררכיה רקורסיבית ההפניה להורה תמיד אופציונלית**, ומעגלים הם סכנה אמיתית שהמבנה לבדו לא מונע.
7. **מידע היסטורי חייב להיות מתוכנן מראש.** ערך שמעדכנים במקום — העבר שלו נמחק לתמיד, ואין דרך לשחזר אותו.
