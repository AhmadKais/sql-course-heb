## 1. למה זמן הוא המימד הקשה ביותר

<div align="center">

**כל עמודה שאתם מעדכנים היא עמודה שאתם מוחקים.**

</div>

זה נשמע דרמטי, וזו פשוט אמת טכנית: `UPDATE` כותב על הערך הקודם. אין "בטל", אין גיבוי שמחזיר ערך בודד, ואין דרך לשחזר בדיעבד מה היה שם.

> 🎬 **סיפור מהשטח: הבונוס שנעלם**
>
> חברה שילמה בונוסים שנתיים לפי אחוז מהמשכורת. בינואר רץ חישוב: 8% לכל עובד.
>
> במרץ עובדת פנתה: *"קיבלתי בונוס לפי משכורת של 12,000, אבל בדצמבר הרווחתי 14,000. איך זה?"*
>
> בדיקה גילתה: המשכורת שלה **ירדה** בפברואר, כי היא עברה למשרה חלקית. החישוב רץ בינואר, אבל הדוח שהופק במרץ שלף את המשכורת **הנוכחית** — 12,000.
>
> ואז התברר הדבר החמור: **גם החישוב עצמו** רץ מול העמודה `salary` בטבלת העובדים. אף אחד לא ידע מה הייתה המשכורת בדצמבר, כי העמודה עודכנה מאז. **לא היה מול מה לבדוק.**
>
> החברה שילמה בונוסים משוערים ל‑340 עובדים והתנצלה בכתב.
>
> 🔑 **הבעיה לא הייתה בקוד החישוב. היא הייתה בכך שהמודל לא ידע שמשכורת היא דבר שמשתנה.**

### 1.1 שלוש השאלות שמפרידות בין מודלים

</div>

```text
+----------------------------------------------------------------------+
| (1) "WHAT IS?"        <- the present                                 |
|     "What is Dana's salary?"                                         |
|     <- a plain column is enough                                      |
+----------------------------------------------------------------------+
| (2) "WHAT WAS?"       <- the past                                    |
|     "What was Dana's salary in December?"                            |
|     <- needs a PERIOD ENTITY  (module 7)                             |
+----------------------------------------------------------------------+
| (3) "WHAT DID WE KNOW?"   <- (!) the past OF THE KNOWLEDGE           |
|     "What did we THINK in January that Dana's December salary was?"  |
|     <- needs a BITEMPORAL MODEL                                      |
+----------------------------------------------------------------------+

  Most systems answer (1).  Good systems answer (2).
  Systems that face an audit must also answer (3).
```

<div dir="rtl">

> 💡 שאלה ③ נשמעת פילוסופית עד שנתקלים בה: *"למה הדוח שהדפסתי בינואר מראה מספר אחר מהדוח שהדפסתי היום על אותו חודש?"* — כי מישהו תיקן נתון בדיעבד. **בלי מודל דו‑זמני אין דרך להסביר את הפער.**

## 2. נקודת זמן מול תקופה

הטעות הראשונה בעיצוב זמן היא לבחור את הצורה הלא נכונה.

</div>

```text
+--------------------------------+------------------------------------+
| POINT IN TIME                  | PERIOD                             |
+--------------------------------+------------------------------------+
| one column: when it happened   | two columns: from when, until when |
|                                |                                    |
| <- an EVENT. Happened, ended,  | <- a STATE. Lasts over time        |
|    never changes               |                                    |
+--------------------------------+------------------------------------+
| vaccination given on 14/09     | animal housed in wing A 14/09-28/09|
| payment made on 03/03          | membership active 01/01 - 31/12    |
| animal taken in on 14/09       | price was 80 NIS, 01/01 - 14/03    |
| message sent at 10:42          | employee in Marketing 2023 - 2025  |
+--------------------------------+------------------------------------+

(!) THE TEST:  "Is this something that HAPPENED, or something that LASTED?"
               happened -> a point.   lasted -> a period.
```

<div dir="rtl">

### ⚠️ המלכודת: אירוע שהוא בעצם תקופה

</div>

```text
"The order was placed on 03/03"   <- looks like a point in time. And it is.

But:
"The order is in status 'shipped'"  <- (!) a DISGUISED PERIOD!
                                       When did it become shipped?
                                       Until when was it so?

The solution:  ORDER_STATUS_HISTORY
         +--------------+------------+-------------+
         | order_id     | status     | from        |
         +--------------+------------+-------------+
         | 5001         | received   | 03/03 09:15 |
         | 5001         | approved   | 03/03 11:40 |
         | 5001         | shipped    | 04/03 08:00 |
         | 5001         | delivered  | 05/03 14:22 |
         +--------------+------------+-------------+

         <- note: there is NO end_date! Each row ends when the next begins.
            This is called an EVENT CHAIN -- simpler than periods,
            and right when the states are SEQUENTIAL and cannot overlap.
```

<div dir="rtl">

| | תקופות (`start` + `end`) | שרשרת אירועים (`from` בלבד) |
|---|--------------------------|------------------------------|
| מתאים ל | מצבים שיכולים לחפוף או להיפסק | מצבים עוקבים בלבד |
| "מה המצב עכשיו?" | `WHERE end_date IS NULL` | השורה עם ה‑`from` הגדול ביותר |
| סיכון | ⚠️ חפיפות, חורים, שתי תקופות פתוחות | ⚠️ קשה לייצג "אין מצב כרגע" |
| דוגמה | שיבוץ לכלוב · תפקיד · מחיר | סטטוס הזמנה · שלבי תהליך |

## 3. המודל הדו‑זמני (Bitemporal)

<div align="center">

**שני צירי זמן שונים לחלוטין, ורוב האנשים לא יודעים שהם קיימים.**

</div>

| הציר | השם | השאלה שהוא עונה עליה |
|------|------|------------------------|
| **זמן תקף** | Valid Time | מתי העובדה **נכונה בעולם** |
| **זמן רישום** | Transaction Time | מתי **המערכת ידעה** עליה |

</div>

```text
An example that explains everything:

  Dana got a raise effective 01/01.
  But payroll only entered it into the system on 20/02.

  +--------------------------------------------------------------+
  |  VALID time:        01/01  <- when the new salary is TRUE     |
  |  TRANSACTION time:  20/02  <- when WE FOUND OUT               |
  +--------------------------------------------------------------+

  Therefore:
    a report produced on 15/02 about January -> shows the OLD salary
    a report produced on 15/03 about January -> shows the NEW salary

    (!) BOTH reports are correct! They answer two different questions:
        "What did we know THEN?"  vs.  "What do we know TODAY?"
```

<div dir="rtl">

### 3.1 המבנה

</div>

```text
SALARY_HISTORY  -- bitemporal
+-------------+----------+--------------+------------+-------------+------------+
| employee_id | amount   | valid_from   | valid_to   | recorded_at | superseded |
+-------------+----------+--------------+------------+-------------+------------+
| 101         | 12,000   | 01/01/2025   | 31/12/2025 | 05/01/2025  | 20/02/2026 |
| 101         | 12,000   | 01/01/2025   | 31/12/2025 | 20/02/2026  | NULL       |
| 101         | 14,000   | 01/01/2026   | NULL       | 20/02/2026  | NULL       |
+-------------+----------+--------------+------------+-------------+------------+
      ^                        ^              ^             ^
    who                 when it is TRUE   when we      when it was replaced
                        in the world      found out    by a corrected row

  "What is Dana's salary in January 2026?"
     -> WHERE valid_from <= '2026-01-15' AND (valid_to IS NULL OR valid_to >= ...)
        AND superseded IS NULL                      <- TODAY's answer

  "What did we think on 01/02 her January salary was?"
     -> same condition, plus: recorded_at <= '2026-02-01'
        AND (superseded IS NULL OR superseded > '2026-02-01')
                                                    <- the answer AS OF THEN
```

<div dir="rtl">

### 3.2 מתי זה הכרחי ומתי זה מוגזם

| ✅ חובה דו‑זמני | ❌ מיותר |
|-----------------|----------|
| שכר, מיסים, ביטוח לאומי | רשימת קשר |
| רשומות רפואיות | קטלוג מוצרים |
| ביטוח (פוליסה שתוקפה רטרואקטיבי) | הגדרות משתמש |
| כל מערכת שעוברת **ביקורת** | נתונים שאף אחד לא מדפיס |
| כשדוח שהופק בעבר חייב להיות ניתן לשחזור | |

> ⚠️ **המחיר של דו‑זמני גבוה:** כל שאילתה מקבלת שני תנאים נוספים, וכל טעות בהם נותנת תשובה שגויה בשקט. **אל תבנו דו‑זמני "ליתר ביטחון".** בנו אותו כשיש דרישה מפורשת — רגולציה, ביקורת, או שאלה עסקית אמיתית מסוג ③.

## 4. שינויים במודל: מחיר

מחיר הוא הדוגמה הקלאסית, כי הוא נוגע בכל שלוש שאלות הזמן **וגם** בכסף.

### 4.1 חמשת המחירים השונים

הטעות הגדולה היא לחשוב ש"מחיר" הוא דבר אחד. הוא לפחות חמישה:

</div>

```text
+----------------------+------------------------------+------------------+
| THE PRICE            | WHAT IT MEANS                | WHERE IT LIVES   |
+----------------------+------------------------------+------------------+
| (1) COST price       | what it cost US              | PURCHASE / SUPPLY|
+----------------------+------------------------------+------------------+
| (2) LIST price       | the official price today     | PRICE_LIST       |
|                      |                              |  <- with validity|
+----------------------+------------------------------+------------------+
| (3) PROMO price      | temporary, for a period or   | PROMOTION        |
|                      | an audience                  |                  |
+----------------------+------------------------------+------------------+
| (4) CUSTOMER price   | personal discount / contract | CUSTOMER_PRICE   |
|                      | / club member                |                  |
+----------------------+------------------------------+------------------+
| (5) PAID price       | * what was ACTUALLY paid,    | ORDER_LINE       |
|                      |   back then                  |  <- frozen forever|
+----------------------+------------------------------+------------------+

  (!) (5) is NOT derived from (2)-(4)! It is computed ONCE, at the moment
      of the transaction, and then locked. Even if all the others change -- it does not.
```

<div dir="rtl">

### 4.2 מחירון עם תוקף

עמודת `price` בטבלת המוצרים עונה רק על *"כמה זה עולה היום"*. ברגע שצריך *"כמה זה עלה במרץ"* — צריך מחירון.

</div>

```text
[X] THE SIMPLE APPROACH              [OK] A PRICE LIST WITH VALIDITY
+----------+---------+               PRICE_LIST
| PRODUCT  | price   |               +----------+-------+------------+------------+
+----------+---------+               | product  | price | valid_from | valid_to   |
| Shirt    | 95      |               +----------+-------+------------+------------+
+----------+---------+               | Shirt    | 80    | 01/01/2025 | 14/03/2026 |
                                     | Shirt    | 95    | 15/03/2026 | NULL       |
  the past is erased on every update +----------+-------+------------+------------+

                                     [OK] "What was the price on 05/03?"  -> 80
                                     [OK] you can enter a FUTURE price in advance!
                                          (valid_from = 01/06, not yet in effect)
```

<div dir="rtl">

> 💡 **היתרון שאף אחד לא חושב עליו:** מחירון עם תוקף מאפשר **לתכנן שינוי מחיר מראש**. מנהל מזין ב‑01/05 שהמחיר עולה ב‑01/06, והמערכת מחליפה לבד. עם עמודה בודדת, מישהו צריך לזכור לעדכן ידנית בדיוק באותו יום.

### 4.3 סדר העדיפויות בין המחירים

כשיש מחירון, מבצע, והנחת לקוח — **מי מנצח?** זו החלטה עסקית שחייבים לשאול.

</div>

```text
THE DECISION TREE -- agreed WITH THE CLIENT, not alone:

    What is the price for customer X, product Y, on date Z?
                    |
                    v
    +-----------------------------------+
    | (1) Is there a personal price     |--YES--> that is the price
    |     agreement for this customer?  |
    +---------------+-------------------+
                    | no
                    v
    +-----------------------------------+
    | (2) Is a promotion active on      |--YES--> the promo price
    |     this date?                    |
    +---------------+-------------------+
                    | no
                    v
    +-----------------------------------+
    | (3) The list price valid on that  |-------> that is the price
    |     date                          |
    +-----------------------------------+

(!) But ASK THE CLIENT:
   . Does a promotion OVERRIDE a personal agreement, or do you take the cheaper?
   . Do discounts STACK?          (10% + 15% = 25%? or 23.5%?)
   . Is there a price FLOOR?      (never below cost)
```

<div dir="rtl">

### 4.4 ⭐ ומעל הכול: המחיר הקפוא

<div align="center">

**כל המבנה למעלה קובע מה **יחושב**. ברגע שההזמנה נסגרת — התוצאה נשמרת, ושוכחת מהכול.**

</div>

</div>

```text
ORDER_LINE
+----------+---------+--------+------------+------------+------------------+
| order_id | product | qty    | unit_price | discount   | price_source     |
+----------+---------+--------+------------+------------+------------------+
| 5001     | Shirt   | 2      | 80.00      | 0          | list price       |
| 5002     | Shirt   | 1      | 72.00      | 10%        | Summer 2026 promo|
+----------+---------+--------+------------+------------+------------------+
                                    ^                          ^
                              frozen forever          * AND WHY it is that price!

  The price_source column is the gold:
  in two years, when someone asks "why did this customer pay 72 and not 80?" --
  there is an answer. Without it, someone burns a whole day investigating.
```

<div dir="rtl">

> 🔑 **הכלל שמסכם את כל הפרק על מחירים:**
> **המחירון עונה על "כמה זה עולה". ההזמנה עונה על "כמה שולם". אלה שתי עובדות שונות, ולעולם לא מסתמכים על הראשונה כדי לענות על השנייה.**

## 5. שלוש שיטות מעקב אחר שינויים

עד כה דיברנו על שמירת **ערכים** לאורך זמן. עכשיו — איך עוקבים אחר **השינוי עצמו**.

</div>

```text
+---------------------------------------------------------------------+
| (1) AUDIT LOG                                                       |
|     one table that records every change in every table              |
|                                                                     |
|     +--------+----------+-------+---------+---------+-------+------+ |
|     | log_id | table    | row_id| column  | old     | new   | who  | |
|     +--------+----------+-------+---------+---------+-------+------+ |
|     | 1      | ANIMAL   | 55    | name    | "Dog"   | "Luna"| Ruti | |
|     | 2      | ANIMAL   | 55    | status  | QUARANT | AVAIL | Vet  | |
|     +--------+----------+-------+---------+---------+-------+------+ |
|                                                                     |
|     [+] uniform . automatic (trigger) . catches everything          |
|     [-] very hard to query . grows huge . everything as text        |
|     <- good for: "who changed it and when" . investigations . audit |
+---------------------------------------------------------------------+
| (2) VERSIONING                                                      |
|     every change creates a WHOLE NEW ROW; the old one stays         |
|                                                                     |
|     +--------+-----+--------+---------+----------+------------+     |
|     | doc_id | ver | title  | content | created  | is_current |     |
|     +--------+-----+--------+---------+----------+------------+     |
|     | 7      | 1   | Policy | ...     | 01/01    | false      |     |
|     | 7      | 2   | Policy | ...     | 15/03    | true   <-  |     |
|     +--------+-----+--------+---------+----------+------------+     |
|                                                                     |
|     [+] easy to restore a whole version . easy to compare           |
|     [-] enormous duplication if only one field changed              |
|     <- good for: documents . contracts . configurations . forms     |
+---------------------------------------------------------------------+
| (3) PERIOD ENTITY  (module 7)                                       |
|     only THE FIELD THAT CHANGES gets its own history                |
|                                                                     |
|     [+] precise . clean . easy to query                             |
|     [-] you must decide up front WHICH field                        |
|     <- good for: price . salary . location . status . assignment    |
+---------------------------------------------------------------------+
```

<div dir="rtl">

### איך בוחרים

| השאלה | ⟵ השיטה |
|--------|----------|
| "מי שינה את זה ומתי?" | ① יומן ביקורת |
| "תחזיר לי את הגרסה מלפני חודש" | ② גרסאות |
| "מה היה הערך של השדה הזה בתאריך X?" | ③ ישות תקופה |
| **"כל התשובות"** | ⟵ ③ לשדות החשובים + ① לשאר |

> 💡 **הצירוף הנפוץ בפועל:** ישות תקופה ל‑2–4 השדות שבאמת נשאלים עליהם, ויומן ביקורת גנרי לכל השאר. **אל תעשו ישות תקופה לכל עמודה** — תקבלו 30 טבלאות ותשנאו את המערכת.

### 5.1 מונח שכדאי להכיר: SCD

בעולם מחסני הנתונים (Data Warehouse) לדפוסים האלה יש שמות תקניים — **Slowly Changing Dimensions**:

| הסוג | מה עושים | מקביל אצלנו |
|------|-----------|--------------|
| **Type 1** | דורסים את הערך. אין היסטוריה | עמודה פשוטה |
| **Type 2** | ⭐ שורה חדשה עם תוקף | **ישות תקופה** |
| **Type 3** | עמודה נוספת: `previous_value` | פשרה חלקית — רק שינוי אחד אחורה |

> 💡 כשתשמעו בראיון עבודה "אתה מכיר SCD Type 2?" — התשובה היא: זו בדיוק ישות התקופה שלמדתם. **אותו רעיון, שם אחר.**

## 6. ⭐ הוספת מימד הזמן למקלט

נראה את הכול יחד, על המודל שבנינו.

### 6.1 מה משתנה במקלט — ומה לעשות עם זה

| מה שמשתנה | השיטה | הנימוק |
|------------|--------|---------|
| מיקום החיה | ③ תקופה | "מי היה בכלוב 4 בחודש האחרון?" |
| מצב בריאותי | ③ תקופה | מעקב רפואי; מתי הבריאה |
| מתנדב אחראי | ③ תקופה | מי טיפל בה כשקרה משהו |
| סטטוס החיה | ③ שרשרת אירועים | מצבים עוקבים: הסגר ⟵ זמינה ⟵ שמורה ⟵ מאומצת. לא חופפים |
| תעריף אימוץ | ③ מחירון | "כמה עלה אימוץ כלב ב‑2024?" |
| משקל החיה | **נקודות זמן** | ⚠️ לא תקופה! כל שקילה היא *אירוע* |
| שם החיה | ① יומן ביקורת | נדיר; מספיק לדעת מי שינה |
| פרטי קשר של מאמץ | ③ תקופה | + מוקפא בתוך האימוץ |
| תכונות אופי | ③ תקופה | ⭐ כלב יכול להשתפר בטיפול! |

> ⚠️ **שימו לב לשתי השורות המפתיעות:**
>
> **משקל** — נראה כמו משהו שמשתנה, אז אולי תקופה? **לא.** כל שקילה היא **מדידה שהתרחשה בתאריך**. אף אחד לא שואל "כמה החיה שקלה בין מרץ למאי" — שואלים "מה השקילות שלה". זו סדרת **נקודות זמן**.
>
> **תכונות אופי** — נראה קבוע, אבל **כלב תוקפני שעבר אילוף יכול להפוך לרגוע**. וזה קריטי: אם ההתאמה למשפחה מתבססת על תכונה שכבר לא נכונה — חוזרים לסיפור של הכלב והתינוק ממודול 9.

### 6.2 מודל התעריפים של המקלט

רותי אמרה: *"400 לכלב, 250 לחתול. לפני שנתיים 300 ו‑200. ומעל גיל 8 — חצי מחיר."* שלושה כללים בתשובה אחת:

</div>

```text
ADOPTION_FEE_SCHEDULE                      <- the price list
+-------------+-----------+--------+------------+------------+
| schedule_id | species   | fee    | valid_from | valid_to   |
+-------------+-----------+--------+------------+------------+
| 1           | Dog       | 300    | 01/01/2022 | 31/12/2023 |
| 2           | Cat       | 200    | 01/01/2022 | 31/12/2023 |
| 3           | Dog       | 400    | 01/01/2024 | NULL       |
| 4           | Cat       | 250    | 01/01/2024 | NULL       |
+-------------+-----------+--------+------------+------------+

FEE_MODIFIER                               <- the discounts
+-------------+----------------------+--------+------------+
| modifier_id | condition            | factor | valid_from |
+-------------+----------------------+--------+------------+
| 1           | animal age >= 8      | 0.5    | 01/01/2022 |
+-------------+----------------------+--------+------------+

ADOPTION                                   <- * and what was ACTUALLY paid
+-------------+-----------+----------+----------------------------+
| adoption_id | animal_id | fee_paid | fee_basis                  |
+-------------+-----------+----------+----------------------------+
| 88          | 55        | 200      | "Dog 400 x 0.5 (age 9)"    |
+-------------+-----------+----------+----------------------------+
                              ^                  ^
                        frozen forever     and WHY -- explainable
                                           three years from now

<- now the 2023 receipt really does show 300, exactly as Ruti demanded.
```

### 6.3 השאלה החדשה שהמודל פותח

עם מימד הזמן, המקלט יכול לענות על שאלות שקודם היו בלתי אפשריות:

| השאלה | הישות שמאפשרת אותה |
|--------|---------------------|
| "כמה זמן חיה מחכה בממוצע לפני אימוץ — והאם זה משתפר?" | שרשרת סטטוס + `INTAKE` |
| "מי טיפל בלונה בשבוע שלפני שחלתה?" | `ANIMAL_CAREGIVER` תקופה |
| "אילו חיות היו בכלוב 4 בזמן ההתפרצות?" | `ANIMAL_PLACEMENT` תקופה |
| "האם האילוף עוזר? כמה כלבים שינו תכונה?" | ⭐ `ANIMAL_TRAIT` תקופה |
| "כמה הכנסנו מדמי אימוץ ב‑2024?" | `ADOPTION.fee_paid` מוקפא |
| "האם העלאת התעריף ב‑2024 הורידה אימוצים?" | ⭐ מחירון + אימוצים לאורך זמן |

> 🎓 **שימו לב לשתי השורות האחרונות.** הן שאלות **ניהוליות**, לא תפעוליות — בדיוק סוג השאלות שרותי צריכה לענות עליהן בבקשת המענק. **מימד הזמן הוא מה שהופך מערכת רישום למערכת שמייצרת תובנות.**

## 7. מובילים בעולם מערכות המידע

תכנית הלימודים מזכירה את הנושא כאן, והקשר הגיוני: **בחירת ספק היא החלטה שמלווה ארגון עשרות שנים** — בדיוק כמו החלטות העיצוב שדיברנו עליהן.

### 7.1 המובילים כיום

| הספק | המוצר המרכזי | איפה פוגשים אותו |
|-------|---------------|-------------------|
| **Oracle** | Oracle Database · MySQL (בבעלותה) | בנקים · ביטוח · ממשלה · ⭐ תכנית הלימודים שלנו |
| **Microsoft** | SQL Server · Azure | ארגונים על סביבת Windows |
| **IBM** | Db2 | מערכות ליבה ותיקות, מיינפריים |
| **PostgreSQL** *(קהילה, לא חברה)* | PostgreSQL | ⭐ קוד פתוח · סטארטאפים · הצומח ביותר בשנים האחרונות |
| **Amazon (AWS)** | RDS · Aurora · DynamoDB | ענן — מריצים את כל השאר בתשתית שלהם |
| **Google** | Cloud SQL · BigQuery | ניתוח נתונים בקנה מידה עצום |

**בעולם ה‑NoSQL:** MongoDB (מסמכים) · Redis (זיכרון) · Cassandra (מבוזר)
⟵ משלימים את הרלציוני, לא מחליפים אותו.

### 7.2 מה זה אומר עבורכם

| התובנה | ההסבר |
|---------|--------|
| **SQL היא הכישור, לא המוצר** | 90% מהתחביר זהה בין כולם. מי שיודע SQL אחד עובר לאחר בשבוע |
| **הבחירה היא לרוב ארגונית** | תקציב, תמיכה, מה שכבר קיים — לא "מי הכי טוב" |
| **מעבר בין ספקים יקר מאוד** | ולכן החלטה שנשארת 20 שנה. בדיוק כמו מודל נתונים |
| **הענן שינה את הכללים** | היום קונים **שירות**, לא רישיון. פחות התקנה, יותר תצורה |
| **⭐ העיצוב אינו תלוי בספק** | כל מה שלמדתם בתשעה מודולים **נכון בכולם**. זה בדיוק היתרון של המודל הרלציוני |

> 🎬 **סיפור מהשטח: המערכת שעברה שלושה ספקים**
>
> חברת ביטוח ישראלית בנתה מערכת ב‑1994 על מיינפריים של IBM. ב‑2006 היא הועברה ל‑Oracle. ב‑2019 היא הועברה שוב, ל‑PostgreSQL בענן.
>
> **מודל הנתונים כמעט לא השתנה.** הישויות `POLICY`, `CLAIM`, `INSURED` והקשרים ביניהן שרדו שלושה ספקים ו‑25 שנה. מה שהוחלף בכל פעם היה קוד, כלים וממשקים.
>
> 🔑 **הלקח:** אתם לומדים את החלק שנשאר. הכלים מתחלפים; **המודל שורד**.

## 10. סיכום המודול

<div align="center">

### 🧠 שבע נקודות

</div>

1. **`UPDATE` הוא מחיקה.** כל עמודה שמתעדכנת במקום — העבר שלה אבד לתמיד, ואין דרך לשחזרו.
2. **שלוש שאלות זמן:** מה יש (עמודה) · מה היה (תקופה) · **מה ידענו** (דו‑זמני).
3. **נקודה מול תקופה:** *"קרה"* ⟵ נקודת זמן. *"נמשך"* ⟵ תקופה. סטטוסים עוקבים ⟵ שרשרת אירועים.
4. **"מחיר" הוא חמישה דברים שונים:** עלות · מחירון · מבצע · מחיר לקוח · **מה ששולם**. רק האחרון מוקפא, והוא אינו נגזר מהאחרים.
5. **שמרו גם את ה"למה".** עמודת `price_source` חוסכת יום חקירה בעוד שנתיים.
6. **שלוש שיטות מעקב:** יומן ביקורת (מי ומתי) · גרסאות (שחזור שלם) · ישות תקופה (ערך בתאריך). בפועל — משלבים.
7. **הכלים מתחלפים, המודל שורד.** מערכת שעברה שלושה ספקים ב‑25 שנה שמרה על אותן ישויות.
