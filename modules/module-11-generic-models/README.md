## 1. למה תרשים לא קריא הוא תרשים שגוי

<div align="center">

**תרשים שהלקוח לא מצליח לקרוא — לא אישר.**
**ותרשים שהמפתח לא מצליח לקרוא — ימומש לא נכון.**

</div>

במודול 3 למדנו את **הסימון**: מה אומר `#`, מה אומרת כף עורב, מתי הקו מקווקו. במודול הזה נלמד את **הפריסה** — איפה לשים כל ישות על הדף.

זה נשמע קוסמטי. הוא לא:

| התרשים | מה קורה בפועל |
|---------|----------------|
| קווים מצטלבים בעשרות מקומות | אי אפשר לעקוב אחרי יחס בעין ⟵ מפספסים אותו |
| ישויות פזורות אקראית | הלקוח לא מזהה את מה שחשוב לו ⟵ לא שואל שאלות |
| 40 ישויות בדף אחד | כולם מהנהנים. אף אחד לא קרא |
| שמות לא עקביים | `CUSTOMER` ליד `orders` ליד `Product_Items` ⟵ נראה מרושל, ומרושל נראה לא אמין |

> 🎬 **סיפור מהשטח: התרשים שתלו על הקיר**
>
> צוות עיצוב הגיש ללקוח ERD של 60 ישויות בדף A3 אחד. גופן 6, קווים מצטלבים, ישויות בכל כיוון. הלקוח הסתכל, אמר "מרשים", וחתם.
>
> ארבעה חודשים לאחר מכן, בהדגמה, מנהלת התפעול שאלה: *"רגע, איפה רואים שקבלן יכול לעבוד בכמה אתרים?"*
>
> התשובה: זה **היה** בתרשים. יחס M:M, פתור כראוי, בפינה השמאלית התחתונה, בין שני קווים שחצו אותו.
>
> רק שהמימוש נעשה לפי מה שהמתכנת **הצליח לקרוא** — והוא קרא 1:M.
>
> 🔑 **התרשים היה נכון. הוא פשוט לא היה קריא — וזה אותו דבר בדיוק.**

## 2. מוסכמות פריסה

שש מוסכמות שהופכות תרשים ממבוך לתמונה. הן מגיעות משיטת Barker/Oracle ומקובלות בתעשייה.

### 2.1 כף העורב פונה דרום‑מזרחה

זו המוסכמה החשובה ביותר, והיא גם הכי פחות מוכרת.

</div>

```text
THE RULE:  place entities so that the "many" end (the crow's foot)
           points DOWN and to the RIGHT.

[OK] CORRECT                          [X] HARDER TO READ
                                                    CUSTOMER
   +----------+                                    +----------+
   | CUSTOMER |                                    |          |
   +----+-----+                                    +----+-----+
        |                                               ^
        | (one)                                         | (many)
        v                                               |
   +----+-----+                                    +----+-----+
   |  ORDER   |   <- many                          |  ORDER   |
   +----+-----+                                    +----------+
        |
        v
   +----------+
   |ORDER_LINE|
   +----------+

   The "one" side is always ABOVE / LEFT.
   The "many" side is always BELOW / RIGHT.

   WHY IT WORKS: the eye reads a diagram like a page. Master entities end up
   at the top, detail entities flow downwards -- and the hierarchy of the
   business becomes visible without reading a single label.
```

<div dir="rtl">

> 💡 **בעברית ובאנגלית כאחד:** המוסכמה היא על **כיוון הזרימה**, לא על שפת הכתיבה. גם בתרשים שמוצג לדוברי עברית — הישות הראשית למעלה, והפירוט יורד למטה.

### 2.2 מינימום הצטלבויות

</div>

```text
[X] BEFORE -- 6 crossings              [OK] AFTER -- 0 crossings

  +-------+     +-------+                +-------+   +-------+
  |   A   |     |   B   |                |   A   |   |   B   |
  +---+---+     +---+---+                +---+---+   +---+---+
      |  \     /    |                        |           |
      |   \   /     |                        |           |
      |    \ /      |                        v           v
      |     X       |                    +---+-----------+---+
      |    / \      |                    |        C          |
      |   /   \     |                    +---------+---------+
      v  /     \    v                              |
  +-------+     +-------+                          v
  |   C   |     |   D   |                      +-------+
  +-------+     +-------+                      |   D   |
                                               +-------+

  A crossing is not a mistake in the model -- it is a mistake in the LAYOUT.
  Moving one box usually removes three crossings.
```

<div dir="rtl">

### 2.3 שאר ארבע המוסכמות

| # | המוסכמה | למה |
|---|----------|------|
| 3 | **הישות המרכזית באמצע** | הישות עם הכי הרבה יחסים במרכז הדף — הקווים יוצאים ממנה לכל הכיוונים במקום לחצות את התרשים |
| 4 | **שמות עקביים** | `CUSTOMER` · `ORDER` · `ORDER_LINE` — תמיד יחיד, תמיד אותיות גדולות, תמיד באותה שפה |
| 5 | **גודל אחיד לישויות** | מלבן גדול נקרא כ"חשוב יותר" גם כשהוא לא. אל תתנו לגודל לשקר |
| 6 | **ללא קווים אלכסוניים** | קווים אופקיים ואנכיים בלבד. העין עוקבת אחריהם; אלכסון מאבד אותה |

> ⚠️ **מוסכמה שאינה מוסכמה:** יש מי שמסדר ישויות לפי סדר אלפביתי. **אל תעשו את זה.** תרשים מסודר לפי **תהליך עסקי**, לא לפי א"ב.

## 3. תחומי נושא — כשהתרשים גדול מדי

<div align="center">

**מעל 15–20 ישויות בדף אחד, התרשים מפסיק להיות כלי תקשורת והופך לקישוט.**

</div>

הפתרון אינו גופן קטן יותר. הפתרון הוא **פיצול לתחומי נושא** (Subject Areas).

</div>

```text
INSTEAD OF: one A3 sheet with 60 entities

DO THIS: one overview + several focused diagrams

  +------------------------------------------------------------+
  |  DIAGRAM 0 -- THE OVERVIEW  (subject areas only)           |
  |                                                            |
  |   +-----------+      +-----------+      +-----------+      |
  |   |  ANIMALS  |----->| ADOPTION  |----->| FOLLOW-UP |      |
  |   +-----------+      +-----------+      +-----------+      |
  |         |                  ^                               |
  |         v                  |                               |
  |   +-----------+      +-----------+                         |
  |   |  MEDICAL  |      |  PEOPLE   |                         |
  |   +-----------+      +-----------+                         |
  |                                                            |
  |   <- 5 boxes. The client understands the whole system      |
  |      in 30 seconds.                                        |
  +------------------------------------------------------------+

  +---------------------------+  +---------------------------+
  | DIAGRAM 1 -- ANIMALS      |  | DIAGRAM 2 -- MEDICAL      |
  |                           |  |                           |
  | ANIMAL . SPECIES . BREED  |  | VET_EXAM . VACCINATION    |
  | INTAKE . PLACEMENT        |  | TREATMENT . VACCINE_TYPE  |
  | LOCATION . TRAIT          |  | VET . CLINIC              |
  |                           |  |                           |
  | <- 8 entities. Readable.  |  | <- 6 entities. Readable.  |
  +---------------------------+  +---------------------------+
```

<div dir="rtl">

**שלושה כללים לפיצול:**

| # | הכלל | ההסבר |
|---|------|--------|
| 1 | **פצלו לפי תהליך עסקי, לא לפי גודל** | "כל מה שקשור לרפואה" — לא "15 הישויות הראשונות" |
| 2 | **ישות שמופיעה בשני תחומים — זה תקין** | `ANIMAL` תופיע בכל תרשים. סמנו אותה כ"ישות משותפת" |
| 3 | **תרשים הסקירה אינו ERD** | הוא מפה. בלי מאפיינים, בלי עוצמה — רק תחומים וזרימה ביניהם |

> 💡 **להצגה בכיתה או ללקוח:** התחילו תמיד מתרשים הסקירה. *"אלה חמשת החלקים של המערכת."* ואז צללו לתחום אחד בכל פעם. אף אחד לא מסוגל לקלוט 60 ישויות בבת אחת — כולל אתכם.

## 4. מה זה מודל גנרי

<div align="center">

**מודל גנרי מחליף כמה ישויות דומות בישות אחת + טבלת סוגים.**

</div>

### הדוגמה הקלאסית

</div>

```text
CONCRETE MODEL -- three separate entities

+------------------+   +------------------+   +------------------+
| PHONE_CALL       |   | EMAIL            |   | MEETING          |
+------------------+   +------------------+   +------------------+
| # call_id        |   | # email_id       |   | # meeting_id     |
| * customer_id    |   | * customer_id    |   | * customer_id    |
| * call_date      |   | * sent_date      |   | * meeting_date   |
| * duration_min   |   | * subject        |   | * location       |
| * agent_id       |   | * body           |   | * attendees      |
+------------------+   +------------------+   +------------------+

         ...and a 4th arrives: WHATSAPP_MESSAGE.
         And a 5th: SMS. And a 6th: video call.
         Every one = a new table + new screens + new reports.


GENERIC MODEL -- one entity + a type table

+------------------+          +--------------------------+
| INTERACTION_TYPE |    1   M | INTERACTION              |
+------------------+----------+--------------------------+
| # type_id        |          | # interaction_id         |
| * name           |          | * customer_id      (FK)  |
|   (call/email/   |          | * type_id          (FK)  |
|    meeting/sms)  |          | * occurred_at            |
| * is_active      |          | * agent_id         (FK)  |
+------------------+          | o duration_min           |
                              | o subject                |
                              | o notes                  |
                              +--------------------------+

         A 4th type arrives -> ONE new ROW in INTERACTION_TYPE.
         Zero schema changes. Zero new screens. Zero new reports.
```

<div dir="rtl">

### מה קנינו ומה שילמנו

| ✅ הרווח | ❌ המחיר |
|----------|----------|
| סוג חדש = שורה, לא טבלה | **מאפיינים אופציונליים** — `duration_min` רלוונטי רק לשיחה |
| שאילתה אחת על כל האינטראקציות | **אי אפשר לאכוף חובה לכל סוג** — `NOT NULL` יחול על כולם או על אף אחד |
| מסך אחד, דוח אחד | הלקוח רואה "אינטראקציה" ולא "שיחה" — **רחוק יותר מהשפה שלו** |
| קוד שלא משתנה עם כל סוג חדש | **תחקור מסובך יותר** — כל שאילתה מסננת לפי סוג |

<div align="center">

**⚠️ זו ההחלטה המרכזית של הפרק: גמישות נקנית במחיר של אכיפה ושל בהירות.**

</div>

## 5. סקאלת ההפשטה

מודל אינו "גנרי" או "לא גנרי" — הוא יושב על סקאלה. תפקידכם לבחור **מיקום**, לא קיצוניות.

</div>

```text
CONCRETE  <---------------------------------------------------->  GENERIC

 Level 1          Level 2            Level 3             Level 4
 SEPARATE         SUPERTYPE +        ONE ENTITY +        EAV
 ENTITIES         SUBTYPES           TYPE TABLE          (attribute rows)

 DOG              ANIMAL             ANIMAL              THING
 CAT               +- DOG             + species_id        + attribute
 RABBIT            +- CAT             (all attributes     + value
 PARROT            +- RABBIT           optional)
                   +- PARROT

 [+] every rule   [+] shared attrs   [+] new type =      [+] infinitely
     enforceable      in one place       one row             flexible
 [+] clearest     [+] type-specific  [-] no per-type     [-] no types,
     to the           rules possible      mandatory           no constraints,
     client       [-] more tables    [-] language drifts     no readable
 [-] 4 tables                            from the client     queries
     to change                                           [-] ** DANGER **

        ^                  ^                 ^                  ^
     modules 2-3       module 4         THIS module      THIS module, sec. 7

 Most real systems live at level 2 or 3. Level 1 for a small closed set;
 level 4 almost never.
```

<div dir="rtl">

> 🔑 **שאלת ההכרעה בין רמה 2 לרמה 3:**
> *"האם לסוגים השונים יש **מאפיינים ייחודיים** — או רק **שם שונה**?"*
>
> מאפיינים ייחודיים (לכלב יש `dog_aggression`, לתוכי יש `wingspan`) ⟵ **רמה 2, טיפוסי משנה**.
> רק שם שונה (שיחה/מייל/פגישה — כולם "משהו שקרה עם לקוח בתאריך") ⟵ **רמה 3, גנרי**.

## 6. שלושה דפוסים גנריים מוכרים

אלה דפוסים שחוזרים בכל תעשייה. שווה להכיר אותם בשם.

### 6.1 `PARTY` — אדם או ארגון

הבעיה: כמעט כל מערכת צריכה גם אנשים וגם חברות, ולשניהם יש כתובות, טלפונים וחוזים.

</div>

```text
+---------------------------+
| PARTY                     |   <- anything that can "act": sign, pay, own
+---------------------------+
| # party_id                |
| * party_type  (PERSON /   |
|                ORGANIZATION)|
| * name                    |
+------------+--------------+
             |
   +---------+---------+
   |                   |
+--+-------------+  +--+----------------+
| PERSON         |  | ORGANIZATION      |
+----------------+  +-------------------+
| * first_name   |  | * legal_name      |
| * last_name    |  | * registration_no |
| * birth_date   |  | * industry        |
+----------------+  +-------------------+

   And then -- ONE address table, ONE phone table, ONE contract table,
   all pointing at PARTY:

   ADDRESS(party_id)  .  PHONE(party_id)  .  CONTRACT(party_id)

   <- instead of person_address + company_address + person_phone + ...
```

<div dir="rtl">

> 💡 זהו בדיוק הפתרון ל"הקשת שהתרבתה" ממודול 7: במקום חמש קשתות `אדם/חברה/עמותה` בחמישה מקומות — ישות `PARTY` אחת שכולם מצביעים אליה.

### 6.2 `EVENT` — משהו שקרה

</div>

```text
+--------------------------+          +------------------------+
| EVENT_TYPE               |   1    M | EVENT                  |
+--------------------------+----------+------------------------+
| # event_type_id          |          | # event_id             |
| * name                   |          | * event_type_id   (FK) |
|   (intake / vaccination /|          | * subject_id      (FK) |
|    adoption / return)    |          | * occurred_at          |
| * subject_entity         |          | * recorded_at          |
| o requires_approval      |          | * performed_by    (FK) |
+--------------------------+          | o notes                |
                                      +------------------------+

  Good for: audit trails, activity feeds, timelines, "what happened to X"
  Bad for:  events with rich, type-specific data
            (an adoption has a fee, an address, a contract -- those do NOT
             belong in a generic EVENT row)
```

<div dir="rtl">

### 6.3 `DOCUMENT` — כל מסמך במערכת

חוזה, קבלה, טופס, אישור — כולם: מספר, תאריך, מנפיק, סטטוס, קובץ מצורף. הדפוס הגנרי חוסך ארבע טבלאות כמעט זהות.

⚠️ **אבל:** חשבונית היא לא "מסמך". יש לה שורות, מע"מ, לקוח ותאריך פירעון. **מסמכים שיש להם מהות עסקית משלהם — נשארים ישויות נפרדות.**

## 7. EAV — הדפוס שהולך רחוק מדי

<div align="center">

**Entity–Attribute–Value: במקום עמודות — שורות.**

</div>

</div>

```text
INSTEAD OF a normal table:
+------------+-------+--------+-----------+
| product_id | name  | colour | weight_kg |
+------------+-------+--------+-----------+
| 101        | Shirt | blue   | 0.3       |
+------------+-------+--------+-----------+

EAV stores this:
+--------+------------+-------------+--------+
| eav_id | product_id | attribute   | value  |
+--------+------------+-------------+--------+
| 1      | 101        | name        | Shirt  |
| 2      | 101        | colour      | blue   |
| 3      | 101        | weight_kg   | 0.3    |
+--------+------------+-------------+--------+

  [+] a new attribute = a new ROW. No schema change. Ever.
  [+] every product can have completely different attributes

  [-] EVERYTHING is text. 0.3 and "0.3" and "zero point three" all fit
  [-] NO data types, NO ranges, NO NOT NULL, NO foreign keys on values
  [-] "products heavier than 1 kg" needs a conversion on every row
  [-] a query for 5 attributes = 5 self-joins
  [-] two people spell the same attribute differently -> silent data loss
```

<div dir="rtl">

### מתי EAV כן מוצדק

הוא לא תמיד פשע. יש שלושה מקרים שבהם הוא הכלי הנכון:

| המקרה | הדוגמה |
|--------|---------|
| **המשתמש מגדיר את השדות** | בונה טפסים, מערכת סקרים, CRM שמאפשר "שדות מותאמים" |
| **מספר עצום של מאפיינים, רובם ריקים** | קטלוג עם 40,000 סוגי מוצרים, לכל אחד 5 מאפיינים משלו |
| **המאפיינים באמת בלתי ידועים מראש** | מדידות ממכשירים שמשתנים כל שנה |

> ⚠️ **ובכל אחד מהם — EAV הוא תוספת, לא תחליף.** השדות הידועים (`name`, `price`, `status`) נשארים עמודות רגילות; רק ה"זנב" הבלתי ידוע הולך ל‑EAV.

> 🎬 **סיפור מהשטח: המערכת שלא ידעה כמה לקוחות יש לה**
>
> סטארטאפ בנה CRM "גמיש לחלוטין": טבלת `ENTITY`, טבלת `ATTRIBUTE`, טבלת `VALUE`. הכול EAV. בלי שום טבלה עסקית.
>
> הרעיון היה מבריק על הנייר: כל לקוח יכול להגדיר לעצמו שדות, ואין צורך לשנות סכימה לעולם.
>
> אחרי שנתיים ביקש המנכ"ל דוח פשוט: *"כמה לקוחות פעילים יש לנו, לפי מדינה?"*
>
> התשובה ארכה יומיים לכתוב, כי:
> - "לקוח" לא היה טבלה — הוא היה `entity_type = 'customer'`, מחרוזת
> - חלק כתבו `'Customer'`, חלק `'customer'`, חלק `'CUST'`
> - "מדינה" נשמרה פעם כ‑`country`, פעם כ‑`Country`, פעם כ‑`state`
> - "פעיל" היה פעם `'yes'`, פעם `'true'`, פעם `'1'`
>
> **המערכת ידעה הכול ולא יכלה לענות על כלום.**
>
> 🔑 גמישות אינסופית פירושה **אפס מבנה** — ובלי מבנה אין שאלות שאפשר לענות עליהן.

## 8. ההכרעה — מתי גנרי ומתי קונקרטי

</div>

```text
                Should I make this generic?
                            |
    +-----------------------+-----------------------+
    |                                               |
 Do the types differ in                    Do they differ only
 ATTRIBUTES and RULES?                     in NAME?
    |                                               |
    v                                               v
 CONCRETE / SUBTYPES                          GENERIC
 (levels 1-2)                                 (level 3)
    |                                               |
    |  Examples:                                    |  Examples:
    |   . dog vs parrot                             |   . call/email/meeting
    |   . checking vs loan account                  |   . document types
    |   . student vs teacher                        |   . event log
    |                                               |
    +-----------------------+-----------------------+
                            |
                  And ALWAYS ask these three:
                            |
    +-----------------------+-----------------------+
    | 1. How often does a NEW TYPE actually appear? |
    |      once a year -> concrete is fine          |
    |      once a month -> generic starts to pay    |
    +-----------------------------------------------+
    | 2. Can the CLIENT still read the model?       |
    |      "interaction" instead of "phone call"    |
    |      is a real loss                           |
    +-----------------------------------------------+
    | 3. Which RULES become unenforceable?          |
    |      list them explicitly. If a critical one  |
    |      is on the list -> do NOT go generic      |
    +-----------------------------------------------+
```

|--------|------------|
| הלקוח אומר "וזה יהיה דומה, רק ש..." הרבה פעמים | 🔁 שקלו גנרי |

| מדובר בליבה העסקית (חשבונית, אימוץ, פוליסה) | 🧱 השארו קונקרטי |

## 9. דוגמה מלאה — מערכת הזמנות לשלושה עסקים

**הסיטואציה:** חברת תוכנה בונה מערכת הזמנות שתשמש **מסעדה, מספרה ומוסך**. שלושתם מזמינים תורים, אבל כל אחד שונה.

### 9.1 הגישה הקונקרטית

</div>

```text
RESTAURANT_BOOKING     SALON_APPOINTMENT      GARAGE_JOB
# booking_id           # appointment_id       # job_id
* customer_id          * customer_id          * customer_id
* datetime             * datetime             * drop_off_date
* guest_count          * stylist_id           * vehicle_id
* table_id             * service_id           * mechanic_id

                       * duration_min         o estimated_ready

  3 tables . 3 sets of screens . 3 reports . 3 of everything
  A 4th client (a dental clinic) = build it all a 4th time
```

### 9.2 הגישה הגנרית

</div>

```text
+--------------------+        +----------------------------+
| BUSINESS           |    1 M | BOOKING                    |
+--------------------+--------+----------------------------+
| # business_id      |        | # booking_id               |
| * name             |        | * business_id        (FK)  |

| * name             |        | BOOKING_DETAIL             |

+--------------------+        | # detail_id                |
                              | * booking_id         (FK)  |
                              | * field_id           (FK)  |
                              | * value                    |
                              +-------------+--------------+
                                            | M
                                            | 1
                              +-------------+--------------+
                              | BUSINESS_FIELD             |
                              +----------------------------+
                              | # field_id                 |
                              | * business_id        (FK)  |
                              | * field_name               |
                              |   (guest_count /           |
                              |    vehicle_plate / ...)    |
                              | * data_type                |
                              | * is_required              |
                              +----------------------------+
```

<div dir="rtl">

### 9.3 הניתוח — מה בדיוק קרה כאן

| | |
|---|---|
| ✅ **מה הרווחנו** | לקוח רביעי = **שורות בטבלה**, לא פרויקט חדש. מסך אחד, דוח אחד, קוד אחד |
| ⚠️ **מה שילמנו** | `BOOKING_DETAIL` הוא **EAV**. "כמה סועדים היו בממוצע?" דורש המרה מטקסט ומסנן לפי `field_id` |
| 🧱 **מה השארנו קונקרטי** | ⭐ `starts_at`, `customer_id`, `status`, `resource_id` — **הם בעמודות אמיתיות**, כי הם קיימים אצל **כל** העסקים ועליהם נשאלות רוב השאלות |

<div align="center">

**וזו התשובה הנכונה: לא גנרי לגמרי ולא קונקרטי לגמרי.**
**הליבה המשותפת בעמודות; הזנב המשתנה ב‑EAV.**

</div>

> 💡 **שימו לב ל‑`BUSINESS_FIELD.is_required`:** זו הדרך להחזיר חלק מהאכיפה שאיבדנו. המערכת לא יכולה לשים `NOT NULL`, אבל היא **כן** יכולה לבדוק בזמן שמירה שכל שדה שמסומן כחובה אצל העסק הזה — מולא. **אכיפה ברמה ③ (אפליקציה), במקום רמה ① (מבנה).** זה פחות טוב, וזה מה שיש.

## 10. אופיה המשתנה של העבודה

תכנית הלימודים מסיימת את הפרק בנושא הזה, והוא רלוונטי בדיוק כאן: **מודלים גנריים הם אחד הביטויים לשינוי בעבודה.**

### 10.1 מה השתנה

| פעם | היום |
|------|-------|
| DBA אחד שמר על בסיס נתונים אחד | מהנדס נתונים שמנהל עשרות מקורות |
| שינוי סכימה = פרויקט של חודשיים | מיגרציות אוטומטיות בכל פריסה |
| הכול רלציוני | רלציוני + מסמכים + זיכרון + אחסון אובייקטים |
| המודל תוכנן פעם אחת, מראש | המודל **מתפתח** לאורך חיי המערכת |
| שרתים בחדר במרתף | ענן, תשלום לפי שימוש |
| מפתחים כתבו SQL ידנית | ORM מייצר שאילתות — ולפעמים גרועות |

### 10.2 מה **לא** השתנה

<div align="center">

**אף אחד מהשינויים האלה לא נוגע בשאלה "מה הישויות ומה היחסים ביניהן".**

</div>

| מה שנשאר | למה |
|-----------|------|
| **מודל שגוי נשאר שגוי** | בענן, ב‑NoSQL, עם ORM — כפילות עדיין יוצרת סתירות |
| **הלקוח עדיין לא יודע מה הוא יודע** | "החוליה החסרה" ממודול 2 היא בעיה אנושית, לא טכנולוגית |
| **מה שלא נשמר — אבד** | אין ענן שמחזיר נתון שלא רשמתם |
| **המודל שורד את הכלים** | ראו את סיפור חברת הביטוח במודול 10: שלושה ספקים, אותן ישויות |

### 10.3 ומה זה אומר עליכם

> 🎬 **סיפור מהשטח: "בשביל מה ללמוד את זה, יש AI"**
>
> תלמיד שאל בשיעור: *"למה ללמוד לעצב בסיסי נתונים, אם אפשר לבקש מכלי AI לייצר סכימה?"*
>
> שאלה הוגנת. המורה ביקש ממנו לנסות — לתאר בשתי שורות מקלט לבעלי חיים ולבקש סכימה.
>
> התוצאה הגיעה תוך שניות, ונראתה מצוין: 8 טבלאות, מפתחות, אינדקסים.
>
> ואז המורה שאל שלוש שאלות:
> 1. *"מה קורה כשחיה חוזרת אחרי אימוץ שנכשל?"* ⟵ הסכימה דרסה את הכניסה הראשונה
> 2. *"איך תדע כמה עלתה כל חיה, כשחשבונית אחת מכסה שמונה?"* ⟵ לא היה לזה מקום
> 3. *"למה שמרת `age` ולא תאריך לידה?"* ⟵ שדה שמזדקן
>
> **הכלי ייצר בדיוק את מה שביקשו ממנו. הוא לא ידע לשאול את רותי את השאלות הנכונות — כי הוא לא ידע שיש מה לשאול.**
>
> 🔑 מה שהשתנה: כתיבת ה‑`CREATE TABLE` נהייתה זולה.
> מה שלא השתנה: **לדעת מה צריך להיות בתוכו.** וזה כל הקורס הזה.

## 13. סיכום המודול

<div align="center">

### 🧠 שבע נקודות

</div>

1. **תרשים לא קריא הוא תרשים שגוי.** הוא יאושר בלי שנקרא, ויימומש לפי מה שהצליחו לפענח.
2. **שש מוסכמות פריסה:** כף עורב דרום‑מזרחה · מינימום הצטלבויות · המרכזית באמצע · שמות עקביים · גודל אחיד · ללא אלכסונים.
3. **מעל 15–20 ישויות — מפצלים לתחומי נושא**, ומתחילים תמיד מתרשים סקירה.
4. **מודל גנרי מחליף ישויות דומות בישות + טבלת סוגים.** הרווח: סוג חדש = שורה. המחיר: אכיפה ובהירות.
5. **ההפשטה היא סקאלה בת ארבע רמות**, לא בחירה בינארית. רוב המערכות נכונות ברמה 2–3.
6. **⚠️ EAV הוא הקצה המסוכן.** מוצדק רק ל"זנב" בלתי ידוע, ולעולם לא לליבה העסקית.
7. **הכלים משתנים, השאלות לא.** `CREATE TABLE` נהיה זול; **לדעת מה צריך להיות בתוכו** — לא.
