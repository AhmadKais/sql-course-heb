## 1. למה בכלל לבנות מודל?

### 1.1 סיפור הפתיחה

> 🎬 **סיפור מהשטח: הבית שנבנה בלי תוכנית**
>
> צוות סטארט‑אפ קטן קיבל פרויקט: מערכת לניהול מכירת כרטיסים להופעות. הם היו אנשים מוכשרים ולחוצים בזמן, אז הם דילגו על שלב התכנון והתחילו לכתוב קוד ישר.
>
> שבוע ראשון: טבלת `EVENTS`, טבלת `TICKETS`. עובד יפה.
> שבוע שלישי: הלקוח מזכיר שלהופעה יכולים להיות **כמה אמנים**. הם דוחפים עמודה `artist2`, `artist3`.
> שבוע חמישי: מסתבר שאותה הופעה מתקיימת ב**כמה תאריכים ובכמה אולמות**. עכשיו `artist2` נמצא בטבלה הלא נכונה בכלל.
> שבוע שמיני: הלקוח שואל בתמימות — "ומה עם מנויי עונה?"
>
> בנקודה הזו הצוות מחק את בסיס הנתונים והתחיל מאפס. שמונה שבועות באשפה.
>
> **מה השתבש?** לא הקוד. הם פשוט מעולם לא שאלו את השאלה *"על אילו דברים העסק הזה מדבר, ואיך הם קשורים זה לזה?"*. שאלה שדיון של יומיים סביב לוח מחיק היה עונה עליה.

<div align="center">

### 📐 מודל נתונים הוא התוכנית האדריכלית של המערכת.

**שינוי קו בתוכנית = מחיקה ועיפרון.**
**שינוי קיר בבניין = פטיש, אבק וכסף.**

</div>

### 1.2 שלוש המטרות של מודל הנתונים

| # | המטרה | ההסבר |
|---|-------|-------|
| 1 | **תקשורת** | שפה משותפת בין המעצב הטכני ללקוח העסקי. הלקוח לא קורא קוד — אבל הוא **כן** יודע להגיד "רגע, לקוח יכול להיות גם ספק אצלנו" כשמראים לו תרשים |
| 2 | **מניעת טעויות** | טעות שמתגלה בשלב המודל עולה דקות. אותה טעות בייצור עולה חודשים |
| 3 | **מעבר מסודר לבנייה** | המודל הוא המפרט שממנו נגזרות הטבלאות, העמודות והאילוצים |

## 2. שלוש רמות המודל

זו אחת ההבחנות החשובות בקורס. אותה מציאות עסקית מתוארת בשלוש רמות הפשטה:

</div>

```text
┌────────────────────────────────────────────────────────────────────┐
│  ① המודל הקונספטואלי  (Conceptual)          "מה?"                  │
│     שפה: עסקית · קהל: הלקוח · תוצר: תרשים ERD                       │
│                                                                    │
│        ┌─────────┐   מזמין   ┌─────────┐                           │
│        │  לקוח   │──────────►│  הזמנה  │        אין טכנולוגיה כאן.  │
│        └─────────┘           └─────────┘        רק העסק.           │
└────────────────────────────────────────────────────────────────────┘
                              │
                              │  מיפוי (פרק 12)
                              ▼
┌────────────────────────────────────────────────────────────────────┐
│  ② המודל הלוגי  (Logical)                   "איך זה מיוצג?"        │
│     שפה: רלציונית · קהל: המפתחים · תוצר: סכימה                     │
│                                                                    │
│     CUSTOMERS(cust_id PK, name, phone)                             │
│     ORDERS(order_id PK, cust_id FK, order_date)                    │
└────────────────────────────────────────────────────────────────────┘
                              │
                              │  מימוש
                              ▼
┌────────────────────────────────────────────────────────────────────┐
│  ③ המודל הפיזי  (Physical)                  "איך זה מאוחסן?"       │
│     שפה: של ה-DBMS · קהל: ה-DBA · תוצר: קוד DDL, קבצים, אינדקסים   │
│                                                                    │
│     CREATE TABLE customers (                                       │
│       cust_id NUMBER(6) PRIMARY KEY,                               │
│       name    VARCHAR2(50) NOT NULL ...                            │
│     ) TABLESPACE users;                                            │
└────────────────────────────────────────────────────────────────────┘
```

<div dir="rtl">

| | קונספטואלי | לוגי | פיזי |
|---|---|---|---|
| **השאלה** | מה קיים בעסק? | איך נייצג את זה? | איך זה יאוחסן בפועל? |
| **הקהל** | הלקוח, המנהל | המפתח, המעצב | ה‑DBA |
| **תלוי טכנולוגיה?** | ❌ לא | 🟡 חלקית (רלציוני) | ✅ מאוד (Oracle≠MySQL) |
| **המונחים** | ישות, מאפיין, יחס | טבלה, עמודה, מפתח | קובץ, בלוק, אינדקס |
| **מתי בקורס** | מודולים 2–4 | פרק 12 | פרקים 26–27 |

> ⚠️ **הטעות הנפוצה ביותר של מתחילים:** לקפוץ ישר לרמה ③. הם פותחים כלי ומתחילים ליצור טבלאות — ומגלים אחרי חודש שהמבנה לא מתאר את העסק. **תמיד מתחילים ברמה ①.**

## 3. ישות (Entity) — אבן הבניין

### 3.1 ההגדרה

> **ישות** היא "דבר" בעל משמעות לעסק, שאנחנו רוצים לאסוף ולשמור עליו מידע.

תנאי הסף — שלוש שאלות. אם התשובה לכולן "כן", זו כנראה ישות:

1. **האם זה משהו שהעסק מדבר עליו?** ("הזמנה", "מטופל")
2. **האם יש לו יותר ממופע אחד?** (עסק לא ינהל טבלה ללקוח יחיד)
3. **האם יש עליו יותר מפרט אחד לשמור?** (אם יש רק שם — כנראה זה מאפיין, לא ישות)

### 3.2 ישות מול מופע — ההבחנה הקריטית

זה מקור לבלבול קבוע במבחנים, אז נחדד:

| | ישות (Entity) | מופע (Instance / Occurrence) |
|---|---|---|
| **מה זה** | ה**סוג**, התבנית, הקטגוריה | דוגמה **ספציפית ואחת** מהסוג |
| **כמות** | אחת | רבים |
| **דוגמה** | `תלמיד` | "דנה לוי, ת.ז. 123456789, כיתה י"ב 3" |
| **בטבלה** | הטבלה עצמה | שורה אחת בטבלה |
| **אנלוגיה** | הטופס הריק | הטופס אחרי שמילאו אותו |

</div>

```text
        הישות:  STUDENT                     ← סוג אחד
        ═══════════════════
                  │
      ┌───────────┼───────────┬─────────────┐
      ▼           ▼           ▼             ▼
  ┌────────┐ ┌────────┐  ┌────────┐   ┌────────┐
  │דנה לוי │ │עומר כהן│  │ליאור   │   │  ...   │  ← מופעים (רבים)
  │  י"ב 3 │ │  י"א 1 │  │  י"ב 3 │   │        │
  └────────┘ └────────┘  └────────┘   └────────┘
```

<div dir="rtl">

### 3.3 מוסכמות שיום

בעולם עיצוב הנתונים (וכך בתכנית הלימודים ובאורקל) נהוג:

| הכלל | דוגמה |
|------|-------|
| שם הישות ב**יחיד** | `EMPLOYEE` ולא `EMPLOYEES` |
| שם באותיות **גדולות** | `CUSTOMER` |
| שם **ברור ועסקי**, לא טכני | `ORDER` ולא `TBL_ORD_01` |
| בעברית — שם עצם ביחיד | `לקוח`, `הזמנה`, `ספר` |

> 💡 **למה יחיד?** כי הישות מתארת את **הסוג**, לא את האוסף. "לקוח הוא אדם שרכש מאיתנו" — משפט הגיוני. "לקוחות הוא אדם ש…" — לא.
> (הערה: בשלב הפיזי, טבלאות נהוג לעיתים לכנות ברבים. זו מוסכמה אחרת ברמה אחרת.)

### 3.4 איך מזהים ישויות בטקסט? — שיטת "שמות העצם"

**הכלל המעשי:** קראו את תיאור הלקוח, וסמנו כל **שם עצם**. הישויות מתחבאות שם.

**דוגמה — תיאור של מספרה:**

> *"אנחנו מספרה עם 4 **ספרים**. **לקוחות** מתקשרים וקובעים **תור** ל**טיפול** מסוים — תספורת, צבע או החלקה. לכל **טיפול** יש **מחיר** ו**משך זמן**. בסוף החודש אני רוצה לדעת כמה כל **ספר** הכניס."*

שמות העצם: ספר, לקוח, תור, טיפול, מחיר, משך זמן, חודש.

עכשיו מסננים:

| המועמד | ישות? | ההחלטה |
|--------|-------|---------|
| ספר (עובד) | ✅ | ישות — יש רבים, יש עליו מידע |
| לקוח | ✅ | ישות |
| תור | ✅ | ישות — יש לו תאריך, שעה, סטטוס |
| טיפול (סוג שירות) | ✅ | ישות — יש לו מחיר ומשך |
| מחיר | ❌ | **מאפיין** של טיפול |
| משך זמן | ❌ | **מאפיין** של טיפול |
| חודש | ❌ | לא ישות — נגזר מתאריך התור |

<div align="center">

**🔑 הכלל: אם ל"דבר" יש רק ערך אחד ואין עליו פרטים נוספים — הוא מאפיין, לא ישות.**

</div>

## 4. מאפיין (Attribute) — הפרטים

### 4.1 ההגדרה

> **מאפיין** הוא פרט מידע יחיד המתאר את הישות. הוא מגדיר, מכמת או מסווג אותה.

לישות `STUDENT`: `שם פרטי`, `שם משפחה`, `תאריך לידה`, `כיתה`, `טלפון`, `ממוצע`.

### 4.2 סיווגי מאפיינים

#### ① חובה מול רשות (Mandatory / Optional)

| הסוג | הסימון | המשמעות | דוגמה |
|------|---------|----------|--------|
| **חובה** | `*` (כוכבית) | חייב להיות ערך בכל מופע | `*שם משפחה` |
| **רשות** | `o` (עיגול) | יכול להיות ריק (NULL) | `o אימייל` |

> ⚠️ **החלטה עסקית, לא טכנית!** האם "טלפון נייד" הוא חובה? התשובה תלויה בעסק. במרפאה — כנראה כן. בספריית בית ספר לכיתה א' — כנראה לא. **תמיד שואלים את הלקוח.**

#### ② פשוט מול מורכב (Simple / Composite)

מאפיין **מורכב** ניתן לפירוק לחלקים בעלי משמעות עצמאית:

</div>

```text
       כתובת מלאה  (מורכב)
            │
    ┌───────┼───────┬────────┐
    ▼       ▼       ▼        ▼
   עיר    רחוב   מספר בית   מיקוד      ← פשוטים
```

<div dir="rtl">

**למה זה חשוב?** אם תשמרו `"תל אביב, הרצל 5"` כמחרוזת אחת — לא תוכלו לענות על "כמה לקוחות יש לי בתל אביב?" בלי לחטט בתוך הטקסט.

<div align="center">

**🔑 כלל הזהב: תמיד פרקו למרכיב הקטן ביותר שתצטרכו לחפש לפיו.**

</div>

#### ③ חד‑ערכי מול רב‑ערכי (Single / Multi‑valued)

| | דוגמה |
|---|---|
| **חד‑ערכי** | `תאריך לידה` — יש בדיוק אחד |
| **רב‑ערכי** | `מספרי טלפון` — לאדם יכולים להיות בית, נייד, עבודה |

> ⚠️ **מאפיין רב‑ערכי הוא דגל אדום.** הוא כמעט תמיד מסתיר **ישות נפרדת**. במקום `טלפון1, טלפון2, טלפון3` בתוך `לקוח`, ניצור ישות `טלפון` עם קשר לישות `לקוח`. נלמד את זה לעומק בפרק הנרמול.

#### ④ מאוחסן מול נגזר (Stored / Derived)

| הסוג | ההגדרה | דוגמה |
|------|---------|--------|
| **מאוחסן** | נשמר פיזית בבסיס הנתונים | `תאריך לידה` |
| **נגזר** | ניתן לחישוב ממאפיינים אחרים | `גיל` = היום − תאריך לידה |

**האם לשמור מאפיין נגזר?** ברירת המחדל — **לא**. גיל שנשמר הופך שגוי כל שנה. סכום הזמנה שנשמר הופך שגוי כשמשנים שורה.
**חריג:** כשהחישוב יקר מאוד ונדרש תדיר, או כשצריך "להקפיא" ערך היסטורי (מחיר בעת הרכישה — הוא **לא** אמור להשתנות כשהמחיר בקטלוג עולה!).

### 4.3 סיכום ויזואלי של ישות עם מאפיינים

</div>

```text
      ┌──────────────────────────────────┐
      │           EMPLOYEE               │   ← שם הישות (יחיד, גדולות)
      ├──────────────────────────────────┤
      │  # employee_id                   │   ← # = מזהה ייחודי (UID)
      │  * first_name                    │   ← * = חובה
      │  * last_name                     │
      │  * hire_date                     │
      │  o email                         │   ← o = רשות
      │  o mobile_phone                  │
      │  * salary                        │
      └──────────────────────────────────┘

      המקרא:   #  מזהה ייחודי      *  חובה      o  רשות
```

## 5. מזהה ייחודי (UID / Identifier) — הלב של המודל

### 5.1 ההגדרה

> **מזהה ייחודי (Unique Identifier)** הוא מאפיין — או צירוף מאפיינים — שערכו **שונה בכל מופע** של הישות, ולכן מאפשר להצביע על מופע יחיד ללא ספק.

זהו המושג שהופך בהמשך ל‑**Primary Key** במודל הלוגי.

### 5.2 שלוש הדרישות ממזהה

| # | הדרישה | מה קורה בלעדיה |
|---|---------|-----------------|
| 1 | **ייחודיות** — אין שני מופעים עם אותו ערך | לא תדעו על מי מדובר |
| 2 | **קיים תמיד** — אף פעם לא NULL | מופע בלי זהות |
| 3 | **יציבות** — לא משתנה לאורך חיי המופע | כל הקשרים אליו נשברים |

### 5.3 סוגי מזהים

| הסוג | ההגדרה | דוגמה |
|------|---------|--------|
| **טבעי / עסקי** | מאפיין שקיים ממילא בעולם האמיתי | ת"ז, ISBN, מספר רישוי |
| **מלאכותי / תחליפי (Surrogate)** | מספר שהמערכת ממציאה, ללא משמעות עסקית | `customer_id = 1001` |
| **מורכב (Composite)** | צירוף של כמה מאפיינים | `(מספר קורס + מספר סמסטר + מספר סטודנט)` |
| **משני (Secondary)** | מזהה חלופי, ייחודי גם הוא | אימייל, שם משתמש |

### 5.4 למה ת"ז היא בחירה גרועה כמזהה?

זו שאלה שנשמעת מוזרה — הרי ת"ז ייחודית! אבל:

| הבעיה | ההסבר |
|-------|--------|
| 😶 **לא תמיד קיימת** | תייר, תינוק בן יום, עובד זר, לקוח מחו"ל — למי יש ת"ז? |
| 🔐 **מידע רגיש** | ת"ז מופיעה בכל טבלה שמקושרת אליה, בכל דוח, בכל לוג — סיוט אבטחתי ורגולטורי |
| ✍️ **טעויות הקלדה** | ספרה אחת שגויה = מיזוג של שני אנשים שונים |
| 🔄 **עשויה להשתנות** | נדיר — אבל קורה (שינוי מעמד, תיקון רשם) |
| 🌍 **לא אוניברסלית** | מה תעשו כשהעסק יתרחב לחו"ל? |

<div align="center">

**🔑 המלצת התעשייה: מזהה מלאכותי כ‑PK, ות"ז כמאפיין רגיל עם אילוץ UNIQUE.**

</div>

כך מקבלים את שני העולמות: מזהה יציב ובטוח לקשרים פנימיים, ואכיפת ייחודיות על הת"ז לצרכים עסקיים.

> 🎬 **סיפור מהשטח: שני האנשים שהיו לאדם אחד**
>
> קופת חולים גדולה השתמשה בת"ז כמפתח ראשי לתיק הרפואי. פקידה הקלידה ספרה אחת שגויה בעת רישום מטופל חדש — והמספר שהתקבל **היה שייך למטופל קיים**.
>
> המערכת לא התלוננה: היא ראתה ת"ז מוכרת, ופשוט **צירפה את המידע הרפואי החדש לתיק של האדם האחר**. שני אנשים שונים, תיק אחד. תרופות של האחד רשומות אצל השני, אלרגיות מעורבבות.
>
> הגילוי הגיע חודשים אחר כך, וההפרדה חזרה דרשה חקירה ידנית של כל רשומה בתיק.
>
> **מה שהיה מונע את זה:** מזהה מלאכותי (`patient_id`) כמפתח. ת"ז שגויה הייתה יוצרת מטופל **חדש** — מטרד קטן שמתגלה מיד — במקום מיזוג שקט של שני בני אדם.

## 6. יחסים בין ישויות — מבט ראשון

זהו הנושא של מודול 3, אבל נניח את היסודות.

> **יחס (Relationship)** הוא קשר עסקי משמעותי בין שתי ישויות.

יחס מתואר בשלושה ממדים:

| הממד | השאלה | האפשרויות |
|------|-------|------------|
| **שם** | מה הקשר? | "מזמין", "לומד ב", "עובד ב" |
| **אופציונליות** | חייב או יכול? | must be / may be |
| **דרגה (Cardinality)** | אחד או רבים? | one / many |

### 6.1 שלושת סוגי היחסים

</div>

```text
① אחד לאחד  (1:1)
   ┌────────┐              ┌──────────┐
   │  עובד  │──────────────│ תא אישי  │      עובד אחד = תא אחד
   └────────┘              └──────────┘

② אחד לרבים  (1:M)   ← הנפוץ ביותר
   ┌────────┐              ┌──────────┐
   │  כיתה  │─────────────<│  תלמיד   │      כיתה אחת = הרבה תלמידים
   └────────┘              └──────────┘      תלמיד אחד = כיתה אחת

③ רבים לרבים  (M:M)
   ┌────────┐              ┌──────────┐
   │ סטודנט │>────────────<│   קורס   │      סטודנט לומד הרבה קורסים
   └────────┘              └──────────┘      קורס נלמד ע"י הרבה סטודנטים
```

<div dir="rtl">

**קריאת יחס נכונה — תמיד בשני הכיוונים:**

> "כל **כיתה** *עשויה להכיל* **תלמידים** אחד או יותר."
> "כל **תלמיד** *חייב להיות משויך* ל**כיתה** אחת בדיוק."

> ⚠️ **הערה חשובה:** יחס M:M לא ניתן למימוש ישיר בבסיס נתונים רלציוני. תמיד מפרקים אותו לשני יחסי 1:M באמצעות **ישות מקשרת**. זהו נושא מרכזי במודול 3 ובפרק 5.

## 7. תשאול יעיל — מציאת החוליה החסרה

זהו אחד הנושאים המפורשים בתכנית הלימודים, והוא **המיומנות המקצועית** של מעצב בסיסי נתונים.

### 7.1 הבעיה: לקוחות לא יודעים מה הם יודעים

הלקוח לא מסתיר מכם מידע. הוא פשוט לא מודע לכך שהוא צריך לספר לכם אותו, כי בשבילו זה **מובן מאליו**.

> 🎬 **סיפור מהשטח: "אה, שכחתי להגיד"**
>
> יועץ בנה מערכת לחנות רהיטים. הלקוח תיאר: "לקוח מזמין מוצר, אנחנו מספקים." פשוט. הוא בנה `לקוח → הזמנה → מוצר`.
>
> בהדגמה הראשונה הלקוח אמר: *"רגע, ואיפה מזינים שהספה מגיעה בשלושה בדים שונים ובארבעה גדלים?"*
>
> היועץ: "לא סיפרת שיש וריאציות."
> הלקוח, בכנות גמורה: *"נו, ברור שיש וריאציות. זו חנות רהיטים."*
>
> הוא לא שיקר. פשוט אף אחד לא שאל.

### 7.2 שיטת החקירה — חמש טכניקות

#### ① שאלות פתוחות לפני סגורות

| ❌ פחות טוב | ✅ טוב יותר |
|---|---|
| "יש לכם לקוחות?" | "ספר לי מי הם הלקוחות שלכם, ומה אתם צריכים לדעת על כל אחד" |
| "אתם שומרים היסטוריה?" | "מה קורה למידע על הזמנה אחרי שהיא הסתיימה?" |

#### ② "תאר לי צעד אחר צעד"

בקשו מהלקוח לתאר **תהליך** מהתחלה לסוף. בתיאור תהליך צצות ישויות שבשאלה ישירה לעולם לא היו עולות.

#### ③ ציד המילים "בדרך כלל" ו"חוץ מ"

<div align="center">

**🚩 כל פעם שהלקוח אומר "בדרך כלל", "לרוב", "חוץ מהמקרה ש…" — עצרו וחפרו.**

</div>

שם מסתתרים החוקים העסקיים האמיתיים. "בדרך כלל לקוח משלם בכרטיס" ⟵ **אז מה עוד?** ⟵ "אה, לקוחות עסקיים מקבלים שוטף+30" ⟵ **הרגע גיליתם ישות `אשראי לקוח` וטיפוס משנה.**

#### ④ שאלות "מה אם" (תרחישי קצה)

- מה אם לקוח מבטל אחרי שהמוצר נשלח?
- מה אם שני עובדים משנים את אותה הזמנה בו זמנית?
- מה אם המחיר משתנה בין ההזמנה לאספקה?
- מה אם מוצר נגמר מהמלאי באמצע ההזמנה?

#### ⑤ הצגה חוזרת (Playback)

חִזרו ללקוח על מה שהבנתם **במילים שלו**, ותנו דוגמה קונקרטית:

> "אז אם אני מבין נכון: דנה מזמינה ספה, ההזמנה נכנסת כ'ממתינה', ורק כשהמחסן מאשר מלאי היא הופכת ל'מאושרת'. נכון?"

ברגע שהלקוח שומע דוגמה ספציפית, המוח שלו קופץ מיד לחריגים.

### 7.3 רשימת תיוג — "החוליה החסרה"

עברו על הרשימה הזו בכל ראיון. אלה הדברים שהכי הרבה פעמים חסרים:

| ✅ | השאלה |
|---|-------|
| ☐ | האם קיימים **מצבים/סטטוסים** לישות? (הזמנה: נקלטה / אושרה / נשלחה / בוטלה) |
| ☐ | האם צריך **היסטוריה**? (מה היה המחיר אתמול? מי היה המנהל בשנה שעברה?) |
| ☐ | האם יש **סוגים שונים** של אותה ישות? (לקוח פרטי מול עסקי ⟵ טיפוסי משנה, מודול 4) |
| ☐ | האם ישות אחת יכולה למלא **כמה תפקידים**? (אדם שהוא גם עובד וגם לקוח) |
| ☐ | האם יש **כמויות** או **מחירים** שיכולים להשתנות עם הזמן? |
| ☐ | מי **מורשה** לראות ולשנות כל נתון? |
| ☐ | מה קורה כשמוחקים? (מחיקה אמיתית או סימון "לא פעיל"?) |
| ☐ | האם יש **ערכים מותרים** מוגבלים? (סטטוס יכול להיות רק אחד מ‑4) |
| ☐ | האם המידע מגיע ממערכת **חיצונית**? |
| ☐ | האם יש **דוחות** שהלקוח חייב, ואי אפשר להפיק מהמודל הנוכחי? |

## 8. דוגמה מלאה מקצה לקצה — מספרה

בואו נבנה מודל שלם מתיאור מילולי.

### 8.1 תיאור הלקוח

> *"יש לנו מספרה עם 4 ספרים. לקוחות מתקשרים או נכנסים וקובעים תור. כל תור הוא לספר מסוים, בתאריך ושעה, לטיפול אחד או יותר — תספורת, צבע, החלקה. לכל טיפול יש מחיר ומשך זמן משוער. אנחנו רוצים לזכור את היסטוריית הטיפולים של הלקוח — במיוחד צבעים, כי לקוחות חוזרים ושואלים 'איזה צבע עשית לי בפעם שעברה?'. בסוף החודש אני רוצה דוח כמה כל ספר הכניס."*

### 8.2 שלב 1 — סימון שמות עצם

ספרים · לקוחות · תור · תאריך · שעה · טיפול · מחיר · משך זמן · היסטוריה · צבע · דוח · חודש

### 8.3 שלב 2 — סינון לישויות

| המועמד | הפסק | הנימוק |
|--------|------|---------|
| ספר | ✅ **ישות** | יש 4, יש עליו מידע (שם, טלפון, אחוז עמלה) |
| לקוח | ✅ **ישות** | רבים, ויש מידע |
| תור | ✅ **ישות** | האירוע המרכזי — תאריך, שעה, סטטוס |
| טיפול (סוג שירות) | ✅ **ישות** | קטלוג השירותים, לכל אחד מחיר ומשך |
| תאריך, שעה | ❌ מאפיין | של `תור` |
| מחיר, משך זמן | ❌ מאפיין | של `טיפול` |
| צבע | 🟡 **מאפיין** | של שורת הטיפול בתור (פירוט הצבע שבוצע) |
| היסטוריה, דוח, חודש | ❌ | לא ישויות — אלה **שאילתות** על הנתונים |

### 8.4 שלב 3 — הישויות עם מאפייניהן

</div>

```text
┌──────────────────────┐        ┌──────────────────────┐
│      STYLIST         │        │      CUSTOMER        │
├──────────────────────┤        ├──────────────────────┤
│ # stylist_id         │        │ # customer_id        │
│ * first_name         │        │ * first_name         │
│ * last_name          │        │ * last_name          │
│ * phone              │        │ * phone              │
│ o commission_pct     │        │ o email              │
│ * hire_date          │        │ o birth_date         │
└──────────────────────┘        │ o notes              │
                                └──────────────────────┘

┌──────────────────────┐        ┌──────────────────────┐
│    APPOINTMENT       │        │      SERVICE         │
├──────────────────────┤        ├──────────────────────┤
│ # appointment_id     │        │ # service_id         │
│ * appt_date          │        │ * service_name       │
│ * appt_time          │        │ * price              │
│ * status             │        │ * duration_min       │
│ o cancel_reason      │        │ o description        │
└──────────────────────┘        └──────────────────────┘

┌──────────────────────────────────────────┐
│           APPOINTMENT_SERVICE            │  ← ישות מקשרת
├──────────────────────────────────────────┤     (כי לתור אחד
│ # appt_service_id                        │      יש כמה טיפולים,
│ * price_charged   ← המחיר בפועל, "מוקפא" │      וטיפול מופיע
│ o color_code      ← "איזה צבע עשית לי?"  │      בהרבה תורים)
│ o stylist_notes                          │
└──────────────────────────────────────────┘
```

<div dir="rtl">

### 8.5 שלב 4 — היחסים

| הישות א' | היחס | הישות ב' | הסוג |
|----------|------|----------|------|
| `CUSTOMER` | קובע | `APPOINTMENT` | 1:M — לקוח אחד, הרבה תורים |
| `STYLIST` | מבצע | `APPOINTMENT` | 1:M — ספר אחד, הרבה תורים |
| `APPOINTMENT` | כולל | `APPOINTMENT_SERVICE` | 1:M — תור אחד, כמה טיפולים |
| `SERVICE` | מופיע ב | `APPOINTMENT_SERVICE` | 1:M — טיפול אחד, בהרבה תורים |

הישות `APPOINTMENT_SERVICE` היא **פתרון** ליחס רבים‑לרבים בין `APPOINTMENT` ל‑`SERVICE`.

### 8.6 שלב 5 — החוליות החסרות שגילינו

שימו לב לשלוש החלטות עיצוב שלא נאמרו במפורש בתיאור:

| ההחלטה | למה |
|---------|------|
| **`status` ב‑APPOINTMENT** | הלקוח לא הזכיר ביטולים — אבל תורים מתבטלים תמיד. שאלנו, וגילינו שכן |
| **`price_charged` נפרד מ‑`price`** | המחיר בקטלוג משתנה. אם נעדכן את מחיר התספורת ל‑2026, **כל הדוחות ההיסטוריים ישתנו רטרואקטיבית**. לכן שומרים את המחיר ששולם בפועל |
| **`color_code`** | זו בדיוק הדרישה שהלקוח כן ציין ("איזה צבע עשית לי") — והיא זו שאילצה ישות מקשרת עם מאפיינים משלה |

<div align="center">

**🔑 מאפיין `price_charged` הוא דוגמה מושלמת לחשיבה של מעצב:**
**לא מה שנכון עכשיו — מה שיישאר נכון בעוד שנתיים.**

</div>

## 9. סיכום המודול

<div align="center">

### 🧠 שש נקודות שחייבים לצאת איתן

</div>

1. **מודל נתונים הוא תוכנית אדריכלית** — שינוי בו זול, שינוי בבניין יקר. הוא משרת תקשורת, מניעת טעויות ומעבר מסודר לבנייה.
2. **שלוש רמות:** קונספטואלי (מה קיים בעסק) → לוגי (איך נייצג) → פיזי (איך יאוחסן). **תמיד מתחילים מהראשונה.**
3. **ישות ≠ מופע.** ישות היא הסוג (`STUDENT`), מופע הוא דוגמה בודדת (דנה לוי). ישות = טבלה, מופע = שורה.
4. **מאפיינים** מסווגים לפי: חובה/רשות (`*` / `o`), פשוט/מורכב, חד/רב‑ערכי, מאוחסן/נגזר. מאפיין רב‑ערכי = דגל אדום לישות חבויה.
5. **מזהה ייחודי (`#`)** חייב להיות ייחודי, קיים תמיד ויציב. **העדיפו מזהה מלאכותי** על פני ת"ז או כל מזהה עסקי.
6. **תשאול הוא מיומנות.** שאלות פתוחות, "תאר צעד אחר צעד", ציד "בדרך כלל", תרחישי "מה אם", והצגה חוזרת. החוליה החסרה כמעט תמיד: סטטוסים, היסטוריה, סוגים וחריגים.
