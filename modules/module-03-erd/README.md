## 1. מה זה ERD ולמה הוא קיים

**ERD** = **E**ntity **R**elationship **D**iagram — תרשים ישויות‑קשרים.

זוהי **מפה ויזואלית** של המודל הקונספטואלי שבנינו במודול 2. במקום לתאר במילים "יש לנו לקוחות שמזמינים הזמנות" — מציירים.

### 1.1 למה תרשים ולא טקסט?

> 🎬 **סיפור מהשטח: הדף שהציל שלושה חודשים**
>
> צוות פיתוח עבד שישה שבועות על מערכת לניהול פרויקטים. המפרט היה מסמך Word בן 40 עמודים, מפורט להפליא, שהלקוח קרא ואישר.
>
> ביום שבו מפתחת חדשה הצטרפה לצוות, היא ביקשה "משהו ויזואלי כדי להתמצא". תוך חצי יום היא ציירה ERD מהמסמך ותלתה אותו על הקיר.
>
> הלקוח נכנס לחדר, הסתכל על הקיר במשך עשר שניות, ואמר: *"רגע. למה יש חץ אחד בין 'פרויקט' ל'מנהל'? לפרויקט גדול יש אצלנו תמיד שני מנהלים — טכני ועסקי."*
>
> המידע הזה הופיע בעמוד 23 של המסמך. הלקוח קרא את המסמך ואישר אותו. אבל הוא לא **ראה** את הסתירה — עד שהיא הייתה קו על דף.
>
> **תרשים ERD חושף בעשר שניות מה ש‑40 עמודי טקסט מסתירים.**

<div align="center">

**📐 ERD הוא כלי תקשורת לפני שהוא כלי תיעוד.**

</div>

### 1.2 סימוני ERD — איזה סימון נלמד?

יש כמה "ניבים" לשרטוט ERD:

| הסימון | מי משתמש | מאפיין ויזואלי |
|---------|-----------|-----------------|
| **Barker / Oracle** | Oracle, תכנית הלימודים | ישות = מלבן מעוגל, קווים עם "כף עורב" |
| **Crow's Foot (IE)** | ERwin, נפוץ בתעשייה | דומה מאוד ל‑Barker |
| **Chen** | אקדמיה | ישות = מלבן, יחס = מעוין |
| **UML Class Diagram** | מפתחי תוכנה | מספרים על הקווים (`0..*`, `1..1`) |

<div align="center">

**בקורס הזה נשתמש בסימון Barker — הסימון של אורקל ושל תכנית הלימודים.**

</div>

## 2. אנטומיה של תרשים Barker

### 2.1 ישות

</div>

```text
      +---------------------------+
      |        EMPLOYEE           |   <- entity name: singular, CAPS
      +---------------------------+
      |  # employee_id            |   <- #  unique identifier (UID)
      |  * first_name             |   <- *  Mandatory
      |  * last_name              |
      |  * hire_date              |
      |  o email                  |   <- o  Optional
      |  o mobile_phone           |
      +---------------------------+

      +------------ LEGEND ------------+
      |  #   unique identifier -- UID  |
      |  *   mandatory attribute       |
      |  o   optional attribute        |
      |  (full Barker notation:        |
      |   a box with rounded corners)  |
      +--------------------------------+
```

<div dir="rtl">

### 2.2 יחס — שלושת המרכיבים

כל קו בתרשים נושא **שלושה** פריטי מידע:

</div>

```text
                       (1) the NAME         (3) CARDINALITY
                         v                       v
      +---------+   "assigned to"             +----------+
      |EMPLOYEE |--------------------------< |DEPARTMENT|
      +---------+  ^                    ^    +----------+
                   |                    |
              (2) OPTIONALITY       "crow's foot" = many
              solid line  = mandatory
              dashed line = optional
```

<div dir="rtl">

| המרכיב | האפשרויות | הסימון |
|---------|------------|---------|
| **① שם** | פועל שמתאר את הקשר | טקסט על הקו, בשני הצדדים |
| **② אופציונליות** | חייב / עשוי | קו **רציף** = חובה · קו **מקווקו** = רשות |
| **③ עוצמה** | אחד / רבים | קו **פשוט** = אחד · **כף עורב** (`<`) = רבים |

### 2.3 ⚠️ ההבחנה שהכי מבלבלת: עוצמה מול אופציונליות

<div align="center">

**אלה שתי שאלות שונות לחלוטין. תמיד שואלים את שתיהן.**

</div>

| | השאלה | האפשרויות | הסימון |
|---|-------|------------|---------|
| **אופציונליות** | האם **חייב** להיות קשר? | must be / may be | רציף / מקווקו |
| **עוצמה** | **כמה** מופעים בצד השני? | one / many | קו / כף עורב |

**ארבעת הצירופים האפשריים בכל צד של קו:**

</div>

```text
   ------------      mandatory, one    "must be related to ... exactly one"

   -----------<      mandatory, many   "must contain ... one or more"

   - - - - - -       optional, one     "may be related to ... one"

   - - - - - -<      optional, many    "may contain ... one or more"
```

<div dir="rtl">

### 2.4 איך קוראים יחס — הנוסחה

<div align="center">

### 🗣️ הנוסחה הקנונית

**כל** `<ישות א'>` **|** *חייב / עשוי* **|** `<שם היחס>` **|** *אחד ובדיוק אחד / אחד או יותר* **|** `<ישות ב'>`

</div>

**דוגמה מלאה:**

</div>

```text
      +----------+                              +----------+
      |DEPARTMENT|---------------------------<  | EMPLOYEE |
      +----------+   "employs"     "assigned to" +----------+
                 ^   dashed   solid  ^
                 |                   |
        optional + many       mandatory + one
```

<div dir="rtl">

**קריאה משמאל לימין:**
> "כל **מחלקה** *עשויה להעסיק* **עובד** אחד או יותר."

**קריאה מימין לשמאל:**
> "כל **עובד** *חייב להיות מוצב ב***מחלקה** אחת ובדיוק אחת."

**למה המחלקה "עשויה" ולא "חייבת"?** כי אפשר להקים מחלקה חדשה לפני שגייסו אליה עובדים. זו **החלטה עסקית** שצריך לאמת מול הלקוח — לא ניחוש.

> 💡 **טיפ למבחן:** אם אתם לא מצליחים לקרוא יחס בקול במשפט תקין — התרשים כנראה שגוי. **קריאה בקול היא כלי הבדיקה הטוב ביותר שיש.**

## 3. שלושת סוגי היחסים

### 3.1 אחד לרבים (1:M) — הנפוץ ביותר

</div>

```text
      +----------+                          +----------+
      |  CLASS   |-----------------------<  | STUDENT  |
      +----------+  "contains"   "studies in" +----------+

      "Each CLASS may contain one or more STUDENTS"
      "Each STUDENT must study in one and only one CLASS"
```

<div dir="rtl">

זהו היחס שממנו מורכבים **רוב** המודלים. בעולם הרלציוני הוא ממומש באמצעות **מפתח זר** בצד ה"רבים" — ל‑`STUDENT` תהיה עמודה `class_id`.

### 3.2 אחד לאחד (1:1) — נדיר, וחשוד

</div>

```text
      +----------+                          +----------+
      | EMPLOYEE |--------------------------|  LOCKER  |
      +----------+  "gets"     "assigned to" +----------+
```

<div dir="rtl">

> ⚠️ **יחס 1:1 הוא כמעט תמיד סימן לבעיה.** אם לכל עובד יש בדיוק תא אישי אחד ולכל תא יש בדיוק עובד אחד — **למה שתי ישויות?** אפשר פשוט להוסיף `locker_number` ל‑`EMPLOYEE`.

**מתי 1:1 כן מוצדק?**

| הסיבה | הדוגמה |
|--------|---------|
| **אופציונליות א‑סימטרית** | רק 5% מהעובדים מקבלים רכב חברה — לא נרצה 20 עמודות ריקות ב‑95% מהשורות |
| **אבטחה** | נתונים רפואיים/משכורת בטבלה נפרדת עם הרשאות שונות |
| **מחזור חיים שונה** | הפרטים נוצרים בזמנים שונים או נמחקים בנפרד |
| **גודל** | שדות ענק (תמונות, מסמכים) שמאטים שאילתות רגילות |

**כלל אצבע:** ראיתם 1:1? עצרו ושאלו "למה לא לאחד?". אם אין תשובה טובה — אחדו.

### 3.3 רבים לרבים (M:M) — הבעיה והפתרון

</div>

```text
      +----------+                          +----------+
      | STUDENT  |>---------------------<   |  COURSE  |
      +----------+  "takes"     "taken by"  +----------+

      "Each STUDENT may take one or more COURSES"
      "Each COURSE may be taken by one or more STUDENTS"
```

<div dir="rtl">

**זה נכון עסקית — ובלתי אפשרי טכנית.**

**למה?** נסו לממש את זה בטבלאות:

- לשים `course_id` בטבלת `STUDENT`? הסטודנט לומד 6 קורסים — צריך 6 עמודות. ומה עם השביעי?
- לשים `student_id` בטבלת `COURSE`? באותה מידה — 200 סטודנטים בקורס.

<div align="center">

**🔑 בבסיס נתונים רלציוני אין דרך לייצג M:M ישירות.**
**תמיד — תמיד — מפרקים אותו לשני יחסי 1:M באמצעות ישות מקשרת.**

</div>

### 3.4 הפירוק — צעד אחר צעד

</div>

```text
    BEFORE:
    +----------+                              +----------+
    | STUDENT  |>--------------------------<  |  COURSE  |
    +----------+                              +----------+


    AFTER:
    +----------+                              +----------+
    | STUDENT  |---+                      +---|  COURSE  |
    +----------+   |                      |   +----------+
                   |                      |
                   v                      v
              +----------------------------------+
              |          ENROLLMENT              |  <- the intersection entity
              +----------------------------------+
              |  # enrollment_id                 |
              |  * student_id   (FK)             |
              |  * course_id    (FK)             |
              |  * enrollment_date               |  * its OWN attributes!
              |  o final_grade                   |
              |  * status                        |
              +----------------------------------+

    Read aloud:
    "Each STUDENT may have one or more ENROLLMENTS"
    "Each ENROLLMENT must be for one and only one STUDENT"
    "Each COURSE may include one or more ENROLLMENTS"
    "Each ENROLLMENT must be for one and only one COURSE"
```

<div dir="rtl">

### 3.5 💎 התובנה החשובה של המודול

<div align="center">

**ישות מקשרת אינה "תרגיל טכני". היא כמעט תמיד ישות עסקית אמיתית שפספסתם.**

</div>

שימו לב מה קרה: ברגע שיצרנו את `ENROLLMENT`, פתאום היה **איפה לשים** את תאריך ההרשמה ואת הציון הסופי. הנתונים האלה לא שייכים לסטודנט (יש לו ציונים שונים בקורסים שונים) ולא לקורס (יש בו ציונים שונים לסטודנטים שונים). **הם שייכים לצומת.**

| היחס M:M | הישות המקשרת | המאפיינים שהיא "פותחת" |
|-----------|---------------|--------------------------|
| סטודנט ↔ קורס | `ENROLLMENT` | תאריך הרשמה, ציון, סטטוס |
| הזמנה ↔ מוצר | `ORDER_LINE` | כמות, מחיר ששולם, הנחה |
| שחקן ↔ קבוצה | `CONTRACT` | תאריך התחלה, סיום, שכר, מספר חולצה |
| רופא ↔ מטופל | `APPOINTMENT` | תאריך, שעה, סיבה, אבחנה |
| ספר ↔ מחבר | `AUTHORSHIP` | סדר המחברים, סוג תרומה |
| חיה ↔ מאמץ | `ADOPTION` | תאריך אימוץ, דמי אימוץ, סטטוס |

> 🎬 **סיפור מהשטח: הישות ששווה מיליון שקל**
>
> חברה בנתה מערכת לניהול קורסים. במודל היה יחס M:M בין `TRAINER` (מדריך) ל‑`COURSE`, והמפתח פירק אותו לישות מקשרת פשוטה `TRAINER_COURSE` עם שני מפתחות זרים בלבד — "רק כדי שזה יעבוד".
>
> חצי שנה אחר כך הגיעה הדרישה: *"צריך לדעת כמה כל מדריך מקבל על כל קורס — התעריף שונה לפי ותק וסוג הקורס."*
>
> אילו הישות המקשרת הייתה מתוכננת כישות עסקית אמיתית מלכתחילה, זו הייתה **עמודה אחת**. במקום זה, המערכת כבר חישבה תשלומים לפי תעריף גלובלי במקום מפוזרים בקוד, והשינוי דרש שכתוב של מודול התשלומים.
>
> **הלקח:** כשאתם יוצרים ישות מקשרת, אל תשאלו "מה המינימום שיגרום לזה לעבוד". שאלו: **"מה נכון על הצומת הזה?"**

## 4. מזהה ייחודי מבוסס יחס — ה‑UID Bar

לפעמים ישות לא יכולה להזדהות לבד — היא נזקקת לישות שהיא תלויה בה.

**דוגמה:** בניין עם דירות. מספר הדירה הוא "12" — אבל "דירה 12" קיימת בכל בניין.

</div>

```text
      +----------+                          +----------+
      | BUILDING |-------------+---------<  |APARTMENT |
      +----------+  "contains" ^ "located in"+----------+
      # building_id            |            # apt_number  <- unique only WITHIN the building!
      * address                |
                          UID Bar
                 (a bar crossing the relationship line)
```

<div dir="rtl">

ה‑**UID Bar** — קו קטן שחוצה את קו היחס — מסמן ש**היחס הוא חלק מהמזהה הייחודי** של הישות.

המשמעות: המזהה של `APARTMENT` הוא **הצירוף** `(building_id, apt_number)`. במודל הלוגי זה יהפוך למפתח ראשי מורכב.

**דוגמאות נוספות:**

| הישות התלויה | הישות שהיא תלויה בה | המזהה |
|---------------|----------------------|--------|
| `ORDER_LINE` | `ORDER` | (מספר הזמנה + מספר שורה) |
| `APARTMENT` | `BUILDING` | (מספר בניין + מספר דירה) |
| `SEAT` | `THEATER_HALL` | (מספר אולם + שורה + מושב) |
| `CHAPTER` | `BOOK` | (ISBN + מספר פרק) |

> 💡 **חלופה מעשית:** אפשר תמיד לתת גם לישות תלויה מזהה מלאכותי משלה (`apartment_id`) ולשמור על הצירוף כאילוץ `UNIQUE`. שתי הגישות לגיטימיות — בתכנית הלימודים ובאורקל מלמדים את שיטת ה‑UID Bar, ובתעשייה נפוץ גם המזהה המלאכותי.

## 5. יחסים מיוחדים

### 5.1 יחס רקורסיבי (Recursive / Self‑Referencing)

ישות שקשורה **לעצמה**.

</div>

```text
                    +------------------+
                    |     EMPLOYEE     |
                    +------------------+
              +---->|  # employee_id   |----+
              |     |  * first_name    |    |
              |     |  * last_name     |    |
              |     |  o manager_id    |    |
              |     +------------------+    |
              |                             |
              +------  "managed by"  -------+
                       "manages"

      "Each EMPLOYEE may be managed by one EMPLOYEE"
      "Each EMPLOYEE may manage one or more EMPLOYEES"
```

<div dir="rtl">

**דוגמאות נוספות:** קטגוריה ⟵ תת‑קטגוריה · חלק ⟵ תת‑חלק (Bill of Materials) · אדם ⟵ הורה · הודעה ⟵ תגובה.

**קריטי:** בקצה שמצביע להורה, האופציונליות חייבת להיות **רשות** — אחרת המנכ"ל צריך מנהל, והמנהל שלו צריך מנהל, לאינסוף.

> 📌 נלמד יחסים רקורסיביים לעומק בפרק 7, ואת השאילתות ההיררכיות עליהם בפרק 21.

### 5.2 קשת (Arc) — "או‑או" בלעדי

לפעמים ישות קשורה **לאחת מכמה** ישויות אפשריות — אבל **רק לאחת**.

</div>

```text
      +----------+         +----------+
      | CUSTOMER |         | SUPPLIER |
      +----+-----+         +-----+----+
           |                     |
           +-------.   .---------+
                   '---'    <- the ARC
                     |
                     |
              +--------------+
              |   PAYMENT    |
              +--------------+

      "Each PAYMENT must be related to ONE customer OR ONE supplier --
       but not both, and not neither"
```

<div dir="rtl">

הקשת מסמנת **בלעדיות (Exclusive OR)**: בדיוק אחד מהיחסים שהיא מקיפה יתקיים בכל מופע.

> 📌 קשתות הן נושא של פרק 7. כאן רק נדע לזהות אותן בתרשים.

---

## 6. דיאגרמות מטריציוניות

זהו נושא מפורש בתכנית הלימודים, והוא **הכלי הפשוט ביותר בקורס** — ואחד השימושיים ביותר.

### 6.1 הבעיה שהוא פותר

כשיש 8 ישויות, יש **28 זוגות אפשריים** של יחסים. עם 12 ישויות — **66 זוגות**. אף אחד לא יזכור לבדוק את כולם. הדיאגרמה המטריציונית מכריחה אתכם **לעבור על כל זוג, אחד אחד**.

### 6.2 איך בונים

1. רשמו את כל הישויות בשורות ובעמודות.
2. עברו על **כל תא** ושאלו: *"האם יש קשר עסקי ישיר בין השניים?"*
3. מלאו את סוג היחס, או `—` אם אין.
4. מלאו רק את **המשולש התחתון** (התרשים סימטרי).

### 6.3 דוגמה — מערכת בית ספר

</div>

```text
                 | STUDENT | CLASS | TEACHER | SUBJECT | GRADE | ROOM
    -------------+---------+-------+---------+---------+-------+------
     STUDENT     |    -    |       |         |         |       |
    -------------+---------+-------+---------+---------+-------+------
     CLASS       |   1:M   |   -   |         |         |       |
    -------------+---------+-------+---------+---------+-------+------
     TEACHER     |   M:M ! |  1:M  |    -    |         |       |
    -------------+---------+-------+---------+---------+-------+------
     SUBJECT     |   M:M ! |  M:M !|  M:M !  |    -    |       |
    -------------+---------+-------+---------+---------+-------+------
     GRADE       |   1:M   |   -   |   1:M   |   1:M   |   -   |
    -------------+---------+-------+---------+---------+-------+------
     ROOM        |    -    |  1:M  |    -    |    -    |   -   |  -

     ! = many-to-many relationship that MUST be resolved into an intersection entity
```

<div dir="rtl">

### 6.4 מה המטריצה מגלה

| הגילוי | המשמעות |
|---------|-----------|
| `TEACHER ↔ STUDENT` = M:M | מורה מלמד הרבה תלמידים, תלמיד לומד אצל הרבה מורים ⟵ צריך ישות מקשרת (שבפועל היא `LESSON` או `TEACHING_ASSIGNMENT`) |
| `SUBJECT ↔ TEACHER` = M:M | מורה מלמד כמה מקצועות ⟵ `TEACHER_QUALIFICATION` |
| `SUBJECT ↔ CLASS` = M:M | ⟵ `CURRICULUM` — תוכנית הלימודים של כיתה |
| 4 יחסי M:M | **4 ישויות מקשרות** שלא היו במודל המקורי! |
| `ROOM ↔ STUDENT` = — | אין קשר **ישיר** — הוא עובר דרך הכיתה. חשוב לא להמציא קשרים מיותרים |

<div align="center">

**🔑 המטריצה גילתה 4 ישויות חסרות בשלוש דקות עבודה.**

</div>

> 💡 **טיפ מקצועי:** בנו את המטריצה **לפני** שאתם משרטטים את התרשים. כך תגיעו לשרטוט עם רשימת יחסים מלאה, במקום לגלות באמצע שחסר לכם משהו.

## 7. דוגמה מלאה מקצה לקצה — חנות מקוונת

בואו נבנה ERD שלם.

### 7.1 התיאור

> *"אנחנו חנות מקוונת. לקוחות נרשמים לאתר, ולכל לקוח יכולות להיות כמה כתובות משלוח. הלקוח מוסיף מוצרים לעגלה ומבצע הזמנה. הזמנה מכילה כמה מוצרים בכמויות שונות. כל מוצר שייך לקטגוריה, ולקטגוריה יכולות להיות תת‑קטגוריות. מוצרים מסופקים על ידי ספקים — ואותו מוצר יכול להגיע מכמה ספקים במחירים שונים. לקוחות יכולים לכתוב ביקורת על מוצר שקנו."*

### 7.2 שלב 1 — הישויות

`CUSTOMER` · `ADDRESS` · `ORDER` · `PRODUCT` · `CATEGORY` · `SUPPLIER` · `REVIEW`

### 7.3 שלב 2 — המטריצה

</div>

```text
              | CUST | ADDR | ORDER | PROD | CAT | SUPP | REV
    ----------+------+------+-------+------+-----+------+-----
     CUSTOMER |  -   |      |       |      |     |      |
    ----------+------+------+-------+------+-----+------+-----
     ADDRESS  | 1:M  |  -   |       |      |     |      |
    ----------+------+------+-------+------+-----+------+-----
     ORDER    | 1:M  | M:1  |   -   |      |     |      |
    ----------+------+------+-------+------+-----+------+-----
     PRODUCT  |  -   |  -   | M:M ! |  -   |     |      |
    ----------+------+------+-------+------+-----+------+-----
     CATEGORY |  -   |  -   |   -   | 1:M  | (R) |      |
    ----------+------+------+-------+------+-----+------+-----
     SUPPLIER |  -   |  -   |   -   | M:M !|  -  |  -   |
    ----------+------+------+-------+------+-----+------+-----
     REVIEW   | 1:M  |  -   |   -   | 1:M  |  -  |  -   |  -

     ! = needs resolving      (R) = recursive relationship (sub-categories)
```

**המטריצה גילתה:** 2 יחסי M:M שדורשים ישויות מקשרות, ויחס רקורסיבי אחד.

### 7.5 שלב 4 — קריאת היחסים המרכזיים

| היחס | הקריאה |
|------|---------|
| CUSTOMER → ADDRESS | "כל לקוח **עשוי להחזיק** כתובת אחת או יותר" · "כל כתובת **חייבת להיות שייכת** ללקוח אחד ובדיוק אחד" |
| CUSTOMER → ORDER | "כל לקוח **עשוי לבצע** הזמנה אחת או יותר" · "כל הזמנה **חייבת להתבצע** על ידי לקוח אחד ובדיוק אחד" |
| ORDER → ORDER_LINE | "כל הזמנה **חייבת להכיל** שורת הזמנה אחת או יותר" ⚠️ · "כל שורת הזמנה **חייבת להשתייך** להזמנה אחת ובדיוק אחת" |
| CATEGORY → CATEGORY | "כל קטגוריה **עשויה להיות תת‑קטגוריה של** קטגוריה אחת" · "כל קטגוריה **עשויה להכיל** תת‑קטגוריה אחת או יותר" |

> ⚠️ **שימו לב ל‑`ORDER → ORDER_LINE`:** כאן האופציונליות היא **חובה** בשני הכיוונים. הזמנה **חייבת** להכיל לפחות פריט אחד — הזמנה ריקה חסרת משמעות עסקית. זו החלטה שצריך לאמת עם הלקוח, וזה בדיוק סוג הדיוק שהופך תרשים למועיל.

### 7.6 שלב 5 — החלטות העיצוב שנעשו כאן

| ההחלטה | הנימוק |
|---------|---------|
| `ADDRESS` כישות נפרדת | מאפיין רב‑ערכי (כמה כתובות ללקוח) ⟵ ישות |
| `ship_address_id` בתוך `ORDER` | ⭐ ההזמנה מצביעה על הכתובת **שנבחרה** — אחרת לא נדע לאן נשלחה |
| `unit_price_charged` ב‑`ORDER_LINE` | הקפאת ערך היסטורי (ראו מודול 2) |
| `cost_price` ב‑`PRODUCT_SUPPLIER` | מחיר העלות תלוי בספק **ובמוצר** — הוא שייך לצומת |
| `parent_category_id` רשות | קטגוריית שורש אין לה הורה |
| `is_active` ולא מחיקה | מוצר שנמכר אי פעם לא נמחק — היסטוריית ההזמנות תלויה בו |

## 8. טעויות נפוצות בתרשימי ERD

| # | השגיאה | איך מזהים | התיקון |
|---|--------|------------|---------|
| 1 | **M:M שלא פורק** | כף עורב בשני הצדדים | ישות מקשרת |
| 2 | **מאפיין שהוא בעצם ישות** | `phone1, phone2, phone3` · `treatment1,2,3` | ישות נפרדת + 1:M |
| 3 | **בלבול עוצמה/אופציונליות** | "כל עובד חייב לנהל עובדים" | לחשוב בנפרד: כמה? האם חובה? |
| 4 | **יחס ללא שם** | קו ערום | לתת פועל בשני הצדדים |
| 5 | **1:1 מיותר** | שתי ישויות עם קשר 1:1 חובה בשני הצדדים | לאחד לישות אחת |
| 6 | **מאפיין נגזר** | `age`, `total`, `count_of` | להסיר; לחשב בשאילתה |
| 7 | **קשר מיותר (מעגל)** | A→B→C וגם A→C ישיר | לבדוק אם A→C **נגזר**; אם כן — למחוק |
| 8 | **מזהה לא יציב** | ת"ז, מספר רישוי, שם | מזהה מלאכותי + UNIQUE |
| 9 | **חוסר סטטוס** | ישות תהליכית ללא שדה מצב | להוסיף `status` |
| 10 | **רקורסיה חובה** | עובד **חייב** מנהל | להפוך לרשות — למנכ"ל אין מנהל |

### 8.1 על שגיאה #7 — הקשר המיותר

</div>

```text
    [X] WRONG -- redundant relationship:

    +--------+        +--------+        +---------+
    |STUDENT |-------<| CLASS  |>-------| SCHOOL  |
    +---+----+        +--------+        +----+----+
        |                                    |
        +------------------------------------+
                    [X] redundant!

    Why redundant: the student's school is DERIVED from their class.
    Why dangerous: someone updates the class and forgets the school
                   -> a student in a class of school A, registered at school B.

    [OK] CORRECT:  STUDENT --< CLASS >-- SCHOOL      (and nothing else)
```

<div dir="rtl">

> ⚠️ **חריג חשוב:** לפעמים הקשר הישיר **כן** נדרש — כשהוא מייצג עובדה **עצמאית**, לא נגזרת. למשל, אם תלמיד יכול להיות רשום לבית ספר אחד אך ללמוד בכיתה של בית ספר אחר (תלמיד משולב) — אז שני הקשרים נושאים מידע שונה, ושניהם נחוצים. **שאלו את הלקוח.**

## 9. רשימת בדיקה לתרשים ERD

לפני שאתם מגישים תרשים, עברו על הרשימה:

| ✅ | הבדיקה |
|---|---------|
| ☐ | לכל ישות יש שם ביחיד, באותיות גדולות |
| ☐ | לכל ישות יש מזהה ייחודי (`#`) |
| ☐ | כל מאפיין מסומן `*` או `o` |
| ☐ | אין מאפיינים נגזרים |
| ☐ | אין מאפיינים רב‑ערכיים |
| ☐ | כל המאפיינים המורכבים פורקו |
| ☐ | לכל יחס יש **שם** בשני הכיוונים |
| ☐ | לכל יחס נקבעה **אופציונליות** (רציף/מקווקו) בשני הצדדים |
| ☐ | לכל יחס נקבעה **עוצמה** (קו/כף עורב) בשני הצדדים |
| ☐ | **אין** יחסי M:M שלא פורקו |
| ☐ | כל יחס ניתן לקריאה בקול במשפט תקין, בשני הכיוונים |
| ☐ | בנינו מטריצה ובדקנו כל זוג ישויות |
| ☐ | אין קשרים מיותרים (מעגלים נגזרים) |
| ☐ | ישויות תהליכיות מכילות שדה סטטוס |
| ☐ | ערכים היסטוריים (מחירים, כתובות) מוקפאים היכן שצריך |

## 10. סיכום המודול

<div align="center">

### 🧠 שבע נקודות שחייבים לצאת איתן

</div>

1. **ERD הוא כלי תקשורת** — הוא חושף בעשר שניות סתירות ש‑40 עמודי טקסט מסתירים.
2. **שלושה מרכיבים בכל יחס:** שם (פועל), אופציונליות (רציף=חובה / מקווקו=רשות), עוצמה (קו=אחד / כף עורב=רבים).
3. **עוצמה ≠ אופציונליות.** שתי שאלות שונות: "כמה?" ו"האם חייב?". תמיד שואלים את שתיהן, בשני הצדדים.
4. **קריאה בקול היא כלי הבדיקה.** אם אי אפשר לקרוא יחס במשפט תקין — התרשים שגוי.
5. **M:M לא ניתן למימוש** בבסיס נתונים רלציוני — תמיד מפרקים לשני 1:M עם ישות מקשרת.
6. **ישות מקשרת היא ישות עסקית אמיתית**, לא תרגיל טכני. היא זו שמחזיקה את המאפיינים של הצומת (ציון, כמות, מחיר, תאריך).
7. **הדיאגרמה המטריציונית** מכריחה לבדוק כל זוג ישויות ומגלה יחסים שפספסתם — עשו אותה **לפני** השרטוט.
