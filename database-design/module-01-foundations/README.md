## 1. פתיחה: למה בכלל להתחיל מכאן?

אתם בקורס SQL. הדבר הראשון שבא לכם לעשות זה לפתוח מחשב ולכתוב `SELECT`. אז למה אנחנו פותחים בפרק שאין בו אפילו שורת קוד אחת?

כי SQL היא **שפה**, ושפה משרתת **רעיון**. אם לא תבינו מה זה בסיס נתונים, למה הוא נראה כמו שהוא נראה, ואיזו בעיה הוא בא לפתור — תדעו לכתוב שאילתות, אבל לא תדעו לתכנן מערכת. וההבדל בין השניים הוא ההבדל בין טכנאי למהנדס.

**🧭 הכלל של המודול הזה: לפני שמבינים איך — מבינים למה.**

## 2. נתונים מול מידע — ההבחנה שהכל מתחיל בה

זו ההבחנה הראשונה, והיא נשמעת טריוויאלית עד שמנסים ליישם אותה.

### 2.1 נתון (Data)

**נתון הוא עובדה גולמית, בודדת, חסרת הקשר.**

הנה נתונים:

</div>

```text
42
"Cohen"
2024-03-17
89.90 NIS
"red"
```

<div dir="rtl">

שימו לב מה קורה לכם בראש כשאתם קוראים את זה: **כלום**. `42` זה מה? גיל? ציון? מספר נעליים? מעלות? אין לכם מושג, ולכן הנתון הזה **חסר ערך** בפני עצמו.

זו התכונה המגדירה של נתון: הוא נכון, הוא מדויק, והוא לא אומר כלום.

### 2.2 מידע (Information)

**מידע הוא נתונים שעברו עיבוד וקיבלו הקשר, ולכן יש להם משמעות.**

ניקח את אותם נתונים בדיוק ונוסיף להם הקשר:

| הנתון הגולמי | ההקשר שהוספנו | המידע שנוצר |
|---|---|---|
| `42` | ציון במבחן של תלמיד | "התלמיד נכשל במבחן" |
| `"כהן"` | שם משפחה של המורה המלמדת | "המורה היא הגב' כהן" |
| `2024-03-17` | תאריך ההזמנה | "ההזמנה בוצעה ב‑17 במרץ" |
| `₪89.90` | מחיר המוצר | "המוצר עולה 89.90 ₪" |

עכשיו יש משמעות. עכשיו אפשר **להחליט** משהו.

> 📌 **הנוסחה:** `נתונים + הקשר + עיבוד = מידע`

### 2.3 ידע ותבונה — שתי הקומות שמעל

בעולם ניהול הידע הארגוני משתמשים בפירמידה בת ארבע קומות, שנקראת **פירמידת DIKW**:

</div>

```text
                    ^
                   / \          WISDOM
                  /   \         "What should we do?"
                 /-----\
                /       \       KNOWLEDGE
               /         \      "Why did it happen?"
              /-----------\
             /             \    INFORMATION
            /               \   "What happened?"
           /-----------------\
          /                   \ DATA
         /                     \"raw facts"
        /-----------------------\
```

<div dir="rtl">

בואו נעלה בפירמידה עם דוגמה אחת, שלב אחרי שלב — חנות בגדים:

| קומה | מה יש בה | דוגמה מהחנות |
|------|----------|--------------|
| **נתונים** | עובדות גולמיות | `147`, `"מעיל"`, `2024-01`, `2024-07` |
| **מידע** | הנתונים בהקשר | "נמכרו 147 מעילים בינואר, ו‑6 מעילים ביולי" |
| **ידע** | דפוסים והסברים | "מכירות מעילים תלויות בעונה — שיא בחורף, שפל בקיץ" |
| **תבונה** | החלטה מושכלת | "נזמין מלאי מעילים בספטמבר, ונפנה מקום במחסן לבגדי ים באפריל" |

**המטרה של כל מערכת מידע ארגונית היא לטפס בפירמידה הזו.** אנחנו אוגרים נתונים — אבל אנחנו רוצים תבונה. בסיס הנתונים הוא רק הקומה התחתונה; SQL הוא המדרגות.

> 🎬 **סיפור מהשטח: הנתון ששווה מיליונים — ולא היה שווה כלום**
>
> רשת סופרמרקטים גדולה שמרה במשך שנים כל שורת קופה: מה נקנה, מתי, ובאיזו חנות. מיליארדי שורות. נתונים מושלמים — וחסרי תועלת, כי איש לא עיבד אותם.
>
> יום אחד מישהו הריץ שאילתה אחת שבדקה אילו מוצרים נקנים **יחד**. התוצאה הפתיעה: קונים שקנו חיתולים בערב יום שישי קנו לעיתים קרובות גם בירה. ההסבר (הידע): אבות צעירים נשלחים לקנות חיתולים בסוף השבוע, ולוקחים לעצמם בירה בדרך.
>
> ההחלטה (התבונה): להעביר את מקרר הבירה קרוב למדף החיתולים. המכירות עלו.
>
> **הנתונים היו שם כל השנים.** מה שהיה חסר זה העיבוד. זו בדיוק העבודה שלכם בקורס הזה.

## 3. מה זה בכלל בסיס נתונים?

### 3.1 ההגדרה

> **בסיס נתונים (Database)** = אוסף **מאורגן** של נתונים **קשורים זה לזה**, המאוחסן באופן קבוע, ומשרת **מספר משתמשים ומספר יישומים** במקביל.

שלוש המילים הקריטיות בהגדרה:

1. **מאורגן** — לא ערימה. יש מבנה, יש כללים, יש סדר.
2. **קשורים** — הנתונים לא חיים לבד. תלמיד קשור לכיתה, כיתה קשורה לבית ספר.
3. **מספר משתמשים** — זה לא הקובץ הפרטי שלכם. זה נכס ארגוני משותף.

### 3.2 DBMS — אל תבלבלו בין השניים

זו טעות נפוצה במבחנים, אז נחדד אותה עכשיו:

| | בסיס נתונים (Database) | מערכת לניהול בסיס נתונים (DBMS) |
|---|---|---|
| **מה זה** | הנתונים עצמם | התוכנה שמנהלת את הנתונים |
| **אנלוגיה** | הספרים בספרייה | הספרן + הקטלוג + חוקי ההשאלה |
| **דוגמאות** | בסיס הנתונים של בית הספר | Oracle, MySQL, SQL Server, PostgreSQL |
| **מי כותב אותו** | הארגון | חברת תוכנה |

**DBMS** = **D**ata**b**ase **M**anagement **S**ystem.

מה ה‑DBMS עושה בשבילנו?

- 🔐 **בקרת גישה** — מי רשאי לראות מה, ומי רשאי לשנות מה
- 🔄 **ניהול גישה מקבילה** — מה קורה כששני אנשים מזמינים את אותו כיסא במטוס באותה שנייה
- 💾 **גיבוי ושחזור** — מה קורה כשנופל החשמל באמצע עדכון
- ✅ **אכיפת שלמות** — לא תוכלו להזין תלמיד לכיתה שלא קיימת
- ⚡ **ביצועים** — אינדקסים, אופטימיזציה של שאילתות
- 🗣️ **שפה** — SQL, הממשק שדרכו מדברים עם הנתונים

## 4. החיים לפני בסיסי הנתונים — גישת הקבצים

כדי להעריך פתרון, צריך להכיר את הכאב שהוא פתר.

לפני שנות ה‑60, וגם הרבה אחריהן, כל מחלקה בארגון ניהלה **קבצים משלה**.

</div>

```text
        +--------------+         +--------------+        +--------------+
        |  Sales dept  |         | Billing dept |        | Shipping dept|
        +------+-------+         +------+-------+        +------+-------+
               |                        |                       |
               v                        v                       v
        +--------------+         +--------------+        +--------------+
        | customers.txt|         | billing.dat  |        | ship_list.xls|
        |--------------|         |--------------|        |--------------|
        | Yossi Levi   |         | Y. Levi      |        | Yossi Levi   |
        | Herzl 5      |         | Herzl 5      |        | Herzl 15     |  <- ?!
        | 050-1234567  |         | 050-1234567  |        | 052-9999999  |  <- ?!
        +--------------+         +--------------+        +--------------+
```

<div dir="rtl">

### 4.1 חמש הבעיות של גישת הקבצים

זו רשימה שכדאי לזכור — היא חוזרת במבחנים:

#### ① כפילות נתונים (Data Redundancy)

אותה כתובת של אותו לקוח נשמרה שלוש פעמים, בשלושה קבצים. בזבוז מקום — אבל זו הבעיה הקטנה.

#### ② חוסר עקביות (Data Inconsistency)

הלקוח עבר דירה והודיע למחלקת מכירות. מכירות עדכנה את הקובץ שלה. גבייה ושילוח — לא שמעו. **עכשיו לארגון יש שלוש אמיתות שונות על אותו אדם.** איזו מהן נכונה? אף אחד לא יודע.

#### ③ תלות בין תוכנית לנתונים (Program‑Data Dependence)

מבנה הקובץ היה **כתוב בתוך התוכנית**. רוצים להוסיף שדה "כתובת אימייל"? צריך לשנות את הקובץ — ואת **כל** התוכניות שקוראות אותו. שינוי קטן הפך לפרויקט של חודשים.

#### ④ קושי בגישה לנתונים

רוצים לדעת "כמה לקוחות מתל אביב קנו מוצר X בשנה שעברה?" — אם התוכנית לא נכתבה מראש לענות על השאלה הזו, צריך לכתוב תוכנית חדשה. **כל שאלה חדשה = פרויקט תכנות חדש.**

#### ⑤ בעיות אבטחה ושיתופיות

איך נותנים למחלקת גבייה לראות רק את שדות החוב, ולא את הפרטים הרפואיים? בקובץ שטוח — או שיש לך את כל הקובץ, או שאין לך כלום.

> 🎬 **סיפור מהשטח: הלקוח שמת פעמיים**
>
> בחברת ביטוח גדולה, מערכת התביעות ומערכת השיווק היו שתי מערכות נפרדות עם שני קבצי לקוחות נפרדים. אדם נפטר, המשפחה הודיעה, ומחלקת התביעות סגרה את התיק כראוי.
>
> שלושה שבועות אחר כך קיבלה המשפחה מכתב שיווקי ממוען לנפטר: *"שלום, שמנו לב שלא חידשת את הפוליסה — בוא נדבר על העתיד שלך!"*
>
> מחלקת השיווק לא עשתה שום דבר רע. פשוט **הנתון על הפטירה מעולם לא הגיע לקובץ שלה.**
>
> זו לא תקלה טכנית. זו תקלה **אדריכלית** — ובדיוק בשבילה המציאו בסיסי נתונים: מקור אמת אחד לכל הארגון.

## 5. ההיסטוריה של בסיסי הנתונים

עכשיו הסיפור המלא — איך הגענו למקום שבו אנחנו נמצאים.

### 🕰️ ציר הזמן

</div>

```text

   |
1950s -----> Magnetic tape . Sequential files
   |
1960s -----> Hierarchical model (IBM IMS) -- a tree . Apollo program
   |
1969  -----> Network model (CODASYL / DBTG) -- a network
   |
1970  -----> * E. F. Codd publishes the relational model paper
   |
1974  -----> IBM develops SEQUEL (later SQL) in project System R
   |
1979  -----> * Oracle V2 -- first commercial relational database
   |

   |

   |

   |

   |
2010s -----> The cloud -- Amazon RDS, Azure SQL, Google Cloud SQL
   |
2020s -----> Big Data . Data Lakes . vector databases for AI
   v
```

<div dir="rtl">

### 5.1 המודל ההיררכי (שנות ה‑60)

הנתונים אורגנו כ**עץ**: לכל רשומה יש הורה אחד בדיוק, ויכולים להיות לה מספר ילדים.

</div>

```text
                    +-------------+
                    |   SCHOOL    |
                    +------+------+
              +------------+------------+
              v            v            v
         +---------+  +---------+  +---------+
         | Class A |  | Class B |  | Class C |
         +----+----+  +----+----+  +----+----+
        +-----+----+       |            |
        v          v       v            v
     +-------+ +-------+ +-------+  +-------+
     |Student| |Student| |Student|  |Student|
     +-------+ +-------+ +-------+  +-------+
```

<div dir="rtl">

**המערכת המפורסמת:** IBM IMS, שנבנתה במקור כדי לנהל את מיליוני החלקים של **תוכנית אפולו** של נאס"א. היא עדיין רצה היום בבנקים.

**היתרון:** מהיר מאוד לשאילתות שהולכות "מלמעלה למטה".

**הבעיה הקטלנית:** מה קורה כשתלמיד לומד בשתי כיתות? בעץ, לכל צומת יש הורה **אחד**. כדי לייצג "רבים לרבים" צריך לשכפל את התלמיד — וחזרנו לכפילות ולחוסר עקביות.

### 5.2 המודל הרשתי (1969)

תיקן את הבעיה: הרשה ליותר מהורה אחד, כלומר **רשת** במקום עץ.

**היתרון:** ייצג יחסי רבים‑לרבים.
**הבעיה:** מורכבות בלתי נסבלת. המתכנת היה צריך לנווט בין ה"סטים" באופן ידני, צעד אחר צעד — כמו לנווט בעיר בלי מפה, רק עם הוראות "ימינה, שמאלה, ישר". שינוי במבנה שבר את כל התוכניות.

### 5.3 1970 — המהפכה של קוד

<div align="center">

> ### 🎬 סיפור מהשטח: המאמר ששינה הכל
>
> </div>
>
> ב‑1970 עבד מתמטיקאי בריטי בשם **אדגר פרנק קוד** (Edgar F. Codd) במעבדות המחקר של IBM בסן חוזה. קוד הסתכל על המודל הרשתי והציק לו דבר אחד: **למה מתכנת צריך לדעת איך הנתונים מאוחסנים כדי לשאול עליהם שאלה?**
>
> הוא פרסם מאמר בשם *"A Relational Model of Data for Large Shared Data Banks"*. הרעיון היה פשוט עד כדי חוצפה:
>
> **"נשמור את הכל בטבלאות. והמשתמש יגיד *מה* הוא רוצה — לא *איך* להביא את זה."**
>
> ב‑IBM לא התלהבו. הייתה להם IMS, היא עבדה, היא הכניסה כסף. הרעיון של קוד נשמע אקדמי ואיטי. הם נתנו לו לפתח אב‑טיפוס בשם **System R**, ובתוכו נולדה שפה בשם **SEQUEL** — Structured English Query Language. בגלל סכסוך על סימן מסחרי היא שונתה ל‑**SQL**.
>
> ואז קרה הדבר המעניין. צעיר בשם **לארי אליסון** (Larry Ellison) קרא את המאמרים ש‑IBM פרסמה, הבין שהם יושבים על זהב שהם לא ממהרים למכור — והקדים אותם. ב‑1979 חברתו שחררה את **Oracle V2**, בסיס הנתונים הרלציוני **המסחרי הראשון בעולם**. (לא הייתה גרסה 1 — הם קראו לה V2 כדי שלקוחות לא יחששו לקנות מוצר ראשון.)
>
> IBM הגיבה עם DB2 רק ב‑1983. **13 שנה** אחרי המאמר של קוד.
>
> **הלקח:** הרעיון הטוב ביותר לא מנצח אוטומטית. מנצח מי שמזהה את ערכו קודם.

### 5.4 למה המודל הרלציוני ניצח?

| התכונה | מה זה נותן |
|---|---|
| **פשטות** | הכל טבלאות. שורות ועמודות. כל אחד מבין טבלה. |
| **עצמאות נתונים** | אפשר לשנות את האחסון הפיזי בלי לגעת בתוכניות |
| **שפה דקלרטיבית** | אומרים *מה* רוצים, ה‑DBMS מחליט *איך* להשיג |
| **בסיס מתמטי** | אלגברה רלציונית — יש הוכחות, לא ניחושים |
| **גמישות** | שאלה חדשה = שאילתה חדשה, לא פרויקט חדש |

השורה התחתונה: **המודל הרלציוני העביר את הנטל מהמתכנת אל המחשב.** זו הסיבה שהוא שולט 50 שנה.

## 6. שישה יתרונות של DBMS — התשובה המסודרת

זו רשימה שכדאי לדעת בעל פה:

| # | היתרון | מה זה אומר בפועל |
|---|--------|-------------------|
| 1 | **מזעור כפילויות** | כתובת הלקוח נשמרת **במקום אחד**. עדכנת — עדכנת לכולם. |
| 2 | **עקביות ושלמות** | ה‑DBMS אוכף חוקים: אי אפשר להזמין מוצר שלא קיים. |
| 3 | **שיתוף נתונים** | כל המחלקות עובדות מול אותו מקור אמת. |
| 4 | **עצמאות נתונים** | שינוי במבנה האחסון לא שובר את היישומים. |
| 5 | **אבטחה והרשאות** | לכל משתמש הרשאות משלו, ברמת טבלה ואפילו עמודה. |
| 6 | **גיבוי, שחזור וטרנזקציות** | נפל החשמל באמצע העברה בנקאית? המערכת מחזירה למצב תקין. |

> 💡 **טרנזקציה (Transaction)** היא רצף פעולות שמתבצע **הכל או כלום**. העברה בנקאית = הורדה מחשבון א' + הפקדה בחשבון ב'. אם רק אחת מהן הצליחה — המערכת מבטלת את שתיהן. נלמד על זה לעומק בפרק 32.

### 7.2 SQL מול NoSQL — לא מלחמה, חלוקת עבודה

בשנות ה‑2000 חברות כמו גוגל ופייסבוק נתקלו בבעיה: המודל הרלציוני מצוין, אבל קשה לפזר אותו על פני 10,000 שרתים. כך נולד **NoSQL**.

| | רלציוני (SQL) | NoSQL |
|---|---|---|
| **מבנה** | טבלאות עם סכימה קבועה | מסמכים / מפתח‑ערך / גרף |
| **חוזק** | עקביות מוחלטת, יחסים מורכבים | גמישות, קנה מידה אופקי עצום |
| **מתאים ל** | בנקאות, ERP, מערכות עסקיות | לוגים, קטלוגים, רשתות חברתיות |
| **דוגמאות** | Oracle, MySQL, PostgreSQL | MongoDB, Cassandra, Redis |

> ⚠️ **אל תיפלו לזה:** NoSQL לא "החליף" את SQL. ב‑2026 רוב מערכות הליבה בעולם — בנקים, ביטוח, בתי חולים, רשויות — רצות על בסיסי נתונים רלציוניים. SQL היא אחת המיומנויות עם אורך החיים הארוך ביותר בהייטק: היא בת יותר מ‑50 שנה **ועדיין** בין הכישורים המבוקשים ביותר.

## 8. מונחי יסוד — טעימה לקראת המשך

לפני שנסיים, שמונה מונחים שנפגוש שוב ושוב. אל תדאגו לזכור הכל עכשיו:

| המונח | בעברית | מה זה |
|-------|--------|-------|
| **Table** | טבלה | מבנה של שורות ועמודות שמחזיק נתונים על נושא אחד |
| **Row / Record** | שורה / רשומה | מופע בודד — לקוח אחד, הזמנה אחת |
| **Column / Field** | עמודה / שדה | תכונה אחת — שם, גיל, מחיר |
| **Primary Key** | מפתח ראשי | העמודה שמזהה שורה **באופן ייחודי** |
| **Foreign Key** | מפתח זר | עמודה שמצביעה על מפתח ראשי בטבלה אחרת — כך נוצר קשר |
| **Schema** | סכימה | המבנה הכולל של בסיס הנתונים |
| **Query** | שאילתה | שאלה שאנחנו שואלים את בסיס הנתונים |
| **DBMS** | מערכת לניהול בסיס נתונים | התוכנה שמנהלת הכל |

הנה איך זה נראה בפועל — טבלת `STUDENTS`:

</div>

```text
      Primary Key
          |
    +-----v-----+--------------+-------+-------------+
    |student_id | student_name | grade |  class_id   |<-- Foreign Key
    +-----------+--------------+-------+-------------+
    |    101    |  Dana Levi   |  12   |      3      |  <- a row (Record)
    |    102    |  Omer Cohen  |  11   |      1      |
    |    103    |  Lior Abu    |  12   |      3      |
    +-----------+--------------+-------+-------------+
          ^             ^
          |             +-- a column (Field)
       this value is UNIQUE -- no two students share an id
```

| 1 | **לומר "בסיס נתונים" כשמתכוונים ל‑DBMS** | אלה שני דברים שונים: הנתונים מול התוכנה שמנהלת אותם. בראיון עבודה זה נשמע מיד | בסיס הנתונים = הספרים · ה‑DBMS = הספרנית והמדפים |

## 11. סיכום המודול

<div align="center">

### 🧠 חמש נקודות שחייבים לצאת איתן

</div>

1. **נתון ≠ מידע.** נתון הוא עובדה גולמית; מידע הוא נתון בהקשר. מעליהם: ידע ותבונה (פירמידת DIKW).
2. **בסיס נתונים ≠ DBMS.** בסיס הנתונים הוא הנתונים; ה‑DBMS הוא התוכנה שמנהלת אותם.
3. **גישת הקבצים נכשלה** בגלל כפילות, חוסר עקביות, תלות תוכנית‑נתונים, קושי בגישה ובעיות אבטחה.
4. **1970 — קוד המציא את המודל הרלציוני**, IBM פיתחה SQL ב‑System R, ואורקל הגיעה ראשונה לשוק ב‑1979.
5. **המודל הרלציוני ניצח** כי הוא פשוט, דקלרטיבי, בעל בסיס מתמטי, ומנתק את התוכנית מהאחסון הפיזי.
