## 1. SQL — המפה המלאה

**SQL** (Structured Query Language) היא השפה של כל בסיסי הנתונים הרלציוניים — Oracle, SQL Server, PostgreSQL, MySQL, SQLite. היא נולדה ב‑IBM בשנות ה‑70, הפכה לתקן ב‑1986, ומאז היא אחת משפות התכנות הוותיקות שעדיין בשימוש יומיומי.

</div>

```text
                                    S Q L
     +-------------+---------------+---------------+-------------+-------------+
     |   DQL       |    DML        |    DDL        |    DCL      |    TCL      |
     |   query     |    change     |    define     |    control  |    transact |
     |             |    rows       |    structure  |    access   |             |
     +-------------+---------------+---------------+-------------+-------------+
     | SELECT      | INSERT        | CREATE        | GRANT       | COMMIT      |
     |  WHERE      | UPDATE        | ALTER         | REVOKE      | ROLLBACK    |
     |  ORDER BY   | DELETE        | DROP          |             | SAVEPOINT   |
     |  JOIN       | MERGE         | TRUNCATE      |             |             |
     |  GROUP BY   |               |               |             |             |
     +-------------+---------------+---------------+-------------+-------------+
     | modules     | module 25     | modules       | module 30   | module 32   |
     | 16-24, 28   |               | 26, 27, 29    |             |             |
     +-------------+---------------+---------------+-------------+-------------+
```

<div dir="rtl">

> 🔑 **SQL היא שפה הצהרתית (declarative):** אומרים **מה** רוצים ("חיות זמינות, ממוינות לפי משקל"), לא **איך** למצוא אותן (איזה אינדקס, באיזה סדר לעבור). בסיס הנתונים מחליט על הדרך. זה ההבדל הגדול מ‑Python או Java, שבהן כותבים כל צעד בעצמכם.

## 2. שאילתות — תזכורת בשקף אחד

</div>

```sql
SELECT   s.name AS species, COUNT(*) AS waiting      -- 5. which columns
FROM     animal a                                    -- 1. which table(s)
JOIN     species s ON s.species_id = a.species_id    --    and how they connect
WHERE    a.status = 'available'                      -- 2. which rows
GROUP BY s.name                                      -- 3. groups
HAVING   COUNT(*) > 1                                -- 4. which groups
ORDER BY waiting DESC                                -- 6. order
LIMIT    3;                                          -- 7. how many
```

<div dir="rtl">

| החלק | המודול |
|------|---------|
| `SELECT`, `FROM`, כינויים, `DISTINCT` | 16 |
| `WHERE`, `LIKE`, `IN`, `BETWEEN`, `IS NULL` | 17 |
| `ORDER BY`, `LIMIT`, `AND`/`OR` | 18 |
| פונקציות — טקסט, מספרים, תאריכים, `CASE`, `COALESCE` | 19, 20 |
| `JOIN` לכל סוגיו | 21, 22 |
| `COUNT`, `SUM`, `GROUP BY`, `HAVING`, תתי‑שאילתות, `UNION` | 23, 24 |

## 3. שינויים בטבלאות — תזכורת בשקף אחד

</div>

```sql
INSERT INTO animal (name, species_id, sex, status) VALUES ('Milo', 2, 'M', 'quarantine');
UPDATE animal SET status = 'available' WHERE animal_id = 21;     -- WHERE !!!
DELETE FROM expense WHERE expense_id = 16;                       -- WHERE !!!

ALTER TABLE animal ADD COLUMN is_neutered INTEGER NOT NULL DEFAULT 0;
```

<div dir="rtl">

| שאילתה (`SELECT`) | שינוי (`INSERT` / `UPDATE` / `DELETE` / `ALTER`) |
|---------------------|----------------------------------------------------|
| לא יכולה לקלקל כלום | יכול לקלקל הכול |
| מריצים כמה שרוצים | `SELECT` לפני, טרנזקציה סביב (מודולים 25, 32) |
| כל אחד בצוות | **אחד** אחראי — ראו סעיף 8 |

## 4. למה בסיס נתונים הוא עבודת צוות

בסיס נתונים של ארגון **אף פעם** לא נבנה על ידי אדם אחד:

</div>

```text
   the client ........... knows the business rules (Ruti)
   the analyst .......... interviews, writes the requirements (modules 2, 8)
   the data designer .... ERD, normalization, mapping (modules 3-7, 12)
   the developer ........ CREATE TABLE, queries, views (modules 16-29)
   the DBA .............. security, backups, performance (modules 29, 30, 32)
   the tester ........... tries to break it (constraints, edge cases)
   the users ............ volunteers, vets -- they will tell you what's missing
```

<div dir="rtl">

ובפרויקט הכיתתי — אתם, ב‑2 או 3, ממלאים את כל התפקידים האלה. **המטרה של המודול: שלא תגלו ביום לפני ההגשה ששניכם כתבתם את אותה טבלה, ואף אחד לא כתב את השאילתות.**

> 🎬 **מהשטח:** סקרים בתעשיית התוכנה מראים שוב ושוב שפרויקטים נכשלים פחות בגלל קוד גרוע, ויותר בגלל **תקשורת** — דרישות לא ברורות, אנשים שעבדו על אותו דבר, החלטות שאף אחד לא תיעד. ראיתם את זה במודול 8: יומן ההחלטות קיים בדיוק בגלל זה.

## 5. תפקידים בצוות

בצוות של 3 — חלוקה מומלצת. **כל אחד אחראי על תחום — אבל כולם כותבים SQL.**

| התפקיד | אחראי על | תוצרים |
|---------|-----------|---------|
| **מוביל/ת עיצוב** | ERD סופי, יומן החלטות, מיפוי (מודול 12) | `erd.pdf`, `decisions.md` |
| **מוביל/ת בנייה** | `build.sql` — `CREATE`, אילוצים, אינדקסים, נתונים | `build.sql`, `constraints_test.sql` |
| **מוביל/ת שאילתות** | 15 השאילתות, Views, התובנות | `queries.sql`, `results.md` |
| **כולם** | הצגה, מסמך, ביקורת על העבודה של האחרים | מצגת, `report.pdf` |

> 💡 **בצוות של 2:** מוביל/ת עיצוב + בנייה, ומוביל/ת שאילתות + מצגת.

> 🔑 **ביקורת עמיתים (code review):** כל קובץ נבדק על ידי **מישהו שלא כתב אותו** לפני שהוא "גמור". מוביל השאילתות מריץ את `build.sql` על מחשב נקי; מוביל הבנייה בודק שהשאילתות מחזירות תוצאות הגיוניות. **הטעויות שאתם לא רואים בקוד שלכם — אחרים רואים מיד.**

## 7. ניהול הפרויקט — פירוק, Kanban, לוח זמנים

### 7.1 פירוק למשימות קטנות

"לכתוב את בסיס הנתונים" היא לא משימה — היא פרויקט. **משימה טובה** היא כזו שאדם אחד יכול לסיים ביום עבודה אחד, ושברור מתי היא גמורה:

| ❌ גדול ועמום | ✅ קטן וברור |
|---------------|---------------|
| לעשות את הטבלאות | `CREATE TABLE customer` עם כל האילוצים, ו‑3 `INSERT` שגויים שנחסמים |
| לכתוב שאילתות | שאילתה 5 (`LEFT JOIN … IS NULL`): "מוצרים שלא נמכרו", עם פלט ותובנה |
| המצגת | 3 שקפים: הלקוח, הבעיה, ה‑ERD |

### 7.2 לוח Kanban

</div>

```text
   TO DO                  IN PROGRESS             REVIEW                 DONE
   +------------------+   +------------------+    +------------------+   +------------------+
   | query 9: monthly |   | CREATE order     |    | CREATE customer  |   | final ERD        |
   | income   (Dana)  |   | (Omar)           |    | (Lina) -> Dana   |   | (Lina)           |
   +------------------+   +------------------+    | reviews          |   +------------------+
   | view: active     |   | test data for    |    +------------------+   | decisions.md     |
   | customers        |   | products (Lina)  |                           | (Lina)           |
   +------------------+   +------------------+                           +------------------+

   rules:  every card has ONE owner.  max 2 cards per person in IN PROGRESS.
           nothing goes to DONE without passing REVIEW by someone else.
```

<div dir="rtl">

**כלים:** Trello, GitHub Projects, Microsoft Planner — או לוח מחיק עם פתקים. **הכלי לא משנה; הכללים משנים.**

### 7.3 פגישת צוות קצרה (stand-up)

פעם בשיעור, 5 דקות, כל אחד עונה על שלוש שאלות:
1. מה סיימתי מאז הפעם הקודמת?
2. מה אני עושה עכשיו?
3. **מה תוקע אותי?** ← השאלה הכי חשובה. "אני לא יודע איך לעשות את שאילתה 11" — עדיף לשמוע את זה בשבוע 2 מאשר בלילה לפני ההגשה.

## 8. עבודה משותפת על קבצי SQL

### 8.1 הבעיה

</div>

```text
   Monday:   Lina has build.sql v1.   Omar copies it.   Dana copies it.
   Tuesday:  Lina adds a CHECK.   Omar adds a table.   Dana fixes a typo.
   Wednesday: three different build.sql files.  Which one is "the" file?
              Omar emails his. Lina copies it over hers -- her CHECK is gone.
```

<div dir="rtl">

### 8.2 שלושה פתרונות, מהפשוט לטוב

| הדרך | איך | מתי מתאים |
|------|-----|-----------|
| **בעלים לכל קובץ** | רק מוביל הבנייה משנה את `build.sql`; אחרים שולחים לו בקשות | צוות קטן, פרויקט קצר |
| **תיקייה משותפת עם היסטוריה** | Google Drive / OneDrive — לכל קובץ יש היסטוריית גרסאות | מינימום הכרחי |
| **Git + GitHub** | כל שינוי הוא commit עם הסבר; אפשר לראות מי שינה מה, ולחזור לכל גרסה | ⭐ הדרך המקצועית — וגם תיק העבודות שלכם |

> 🔑 **הכלל הבסיסי, בכל דרך:** `build.sql` אחד, **במקום אחד**, ש**תמיד** רץ. מי ששובר אותו — מתקן לפני שהולך הביתה.

### 8.3 Git — חמש פקודות מספיקות

</div>

```text
   git clone <url>                  get the team's repository (once)
   git pull                         get the latest changes -- BEFORE you start working
   git add build.sql                mark the file you changed
   git commit -m "add CHECK on price"   save a version, with an explanation
   git push                         share it with the team
```

<div dir="rtl">

> 💡 **הודעת commit טובה** אומרת **מה ולמה**: `"add chk_order_qty: quantity must be >= 1 (rule 7)"` — לא `"fix"` או `"changes"`. בעוד חודש, היא התיעוד היחיד של למה האילוץ קיים.

## 9. סיכונים — ומה עושים איתם

**סיכון** = משהו שעוד לא קרה, אבל עלול לקרות ולפגוע בפרויקט. מנהלי פרויקטים כותבים אותם **מראש**:

| הסיכון | הסבירות | ההשפעה | מה עושים מראש |
|--------|----------|---------|-----------------|
| חבר צוות חולה בשבוע האחרון | בינונית | גבוהה | כל אחד מכיר את כל הקבצים (ביקורת עמיתים) |
| `build.sql` לא רץ על המחשב של המורה | בינונית | גבוהה | להריץ על מחשב נקי כל שבוע |
| שאילתה מחזירה ריק כי חסרים נתונים | גבוהה | בינונית | לתכנן את הנתונים **לפי** השאילתות (מודול 31, סעיף 4) |
| המחשב קורס בהדגמה החיה | נמוכה | גבוהה | צילומי מסך של כל שלב |
| הלקוח (המורה) משנה דרישה | בינונית | בינונית | יומן החלטות; עיצוב מנורמל שקל להרחיב |

> 🔑 **סיכון שנכתב — כבר חצי מטופל.** הצוות שכתב "מה אם המחשב קורס?" — הכין צילומי מסך. הצוות שלא כתב — עומד מול הכיתה עם מסך שחור.

## 10. סיכום המודול

<div align="center">

### 🧠 שש נקודות

</div>

1. **SQL = חמש תת‑שפות:** DQL (`SELECT`), DML (`INSERT`…), DDL (`CREATE`…), DCL (`GRANT`), TCL (`COMMIT`). שפה **הצהרתית** — "מה", לא "איך".
2. **שאילתה לא מקלקלת; שינוי — כן.** `SELECT` לפני, טרנזקציה סביב, ואחראי אחד ל‑`build.sql`.
3. **תפקידים:** עיצוב, בנייה, שאילתות — וכולם בודקים את העבודה של כולם.
4. **משימות קטנות וברורות, על לוח Kanban,** עם בעלים אחד לכל משימה ו‑"Review" לפני "Done".
5. **קובץ אחד במקום אחד, עם היסטוריה** — Drive במינימום, Git כמקצוענים.
6. **סיכונים — כותבים מראש.** מה שנכתב, כבר חצי מטופל.
